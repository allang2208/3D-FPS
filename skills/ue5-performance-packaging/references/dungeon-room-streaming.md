# 地牢资源准备与房间可见性

用于大型作者房间组合的加载和绘制优化。源码落盘或导入成功不证明 FPS 提升；同场景实测仅在用户要求时开展。

- 异步加载解决准备阶段等待，不会自动减少运行时同屏灯光、材质和几何开销。按当前抽中布局收集资源，分批 RequestAsyncLoad，保留有效 handle，结束或取消时释放对应请求。
- 保存地图时可将旧导入器提供的硬引用转换为软烹饪依赖；运行时再加载选中路线。反射 UPROPERTY 保留打包依赖，不能只把路径放在任意 JSON 中就假定 Cooker 会收录。真正资源卸载需要另外明确生命周期，隐藏模型不等于卸载。
- 新布局分阶段准备期间保留旧场景和旧资源；只有准备完成才替换。失败/取消不应清空旧场景仍使用的强引用。状态报告区分布局成功、资源准备、物理/导航准备与正式提交。
- 多房共享 ISM 的可见性采用所属房间并集：任一房需要显示就保留整个组件。隐藏只改渲染，不关闭碰撞、搜寻、采集、遭遇或宝箱身份。新近/转向可见的房间优先立即恢复，远处隐藏有预算并带延迟，避免镜头转动时排队露空。
- 单视角调度只用于独立单人视图；分屏和联机不能把第一个玩家的可见性当全局状态。阴影、反射和门外相邻空间需要保留距离，不能只按是否在视锥中裁掉。
- 故障灯的发光表面与实际照明必须使用相同的故障节奏，并与房间灯光调度兼容。材质重导入保留 ISM usage、Nanite/LOD、碰撞和光源单位；编辑器临时编译正确不代表资产已保存正确。

本机实现：`Source/FPSGAME/Dungeons/AuthoredDungeonGenerator.*`、`AuthoredDungeonLighting.*`；迁移作者入口 `SourceAssets/DungeonPerformance20261008/install.py`。本次实现尚无同条件 FPS 对比，不能由房间数、面数或理论纹理大小推算性能收益。
