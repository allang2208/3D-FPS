# FPSGAME 场景开发：交互、直达预览与样板退役

用户确定于 2026-10-01。适用于新房间、楼梯、平台及独立场景主体开发；替代旧案例中“样板必须加入祭坛出征菜单”的默认要求。

## 制作与预览

1. 使用当前工程 `D:/FPS3D/FPSGAME`。复用已认可的模型、材质、灯光和交互；规则结构按实际尺寸制作。作者配置、可编辑源、导出物和正式资产分别保留。
2. 主体阶段独立保存 `/Game/GameMaps/Design/L_<Room>_Subject`，配置正常 FPS GameMode、有效 PlayerStart、连续可走地面和必要碰撞。尚未认可的样板不提前加入随机池。
3. 默认通过游戏控制台 `open <完整地图包路径>` 进入，交付具体命令。无需新增祭坛出征菜单项、正式传送入口或专用 C++ 入口。地图包路径不含 `.umap`，不凭文件显示名猜路径。
4. 预览方式以本机编辑器/开发运行内容为默认。只有用户要求在打包游戏中预览，才把需要的样板加入临时烹饪清单；控制台命令不能加载未烹饪地图。不把所有临时样板永久加入 `MapsToCook`。
5. 交付必要的返回主场景命令；场景已有返回传送门可在预览阶段保留，但正式模块不带它。预览期间不改主场景默认地图。
6. 继续遵守后台制作、必要构建/导入/保存、不主动打开编辑器、不主动测试的约定。控制台命令交给用户执行，不因交付命令而自行进入游戏或截图。

净化站与货运仓库均已获用户确认，已接入三条固定主题路线并归档样板。仓库的主体、精修资产、拖车、灯光与栏杆交互随正式模块保留；旧样板地图及直达命令已退役。

正式随机地牢为 `/Game/GameMaps/L_Dungeon_Randomized`。主题内部顺序固定，基础设施房只在组合前后补充；三路汇流后进入数据档案中心，再通往 Boss。任意一路清理完毕并清理档案中心即可开启 Boss 通路。制作与未测试边界见工程 `Docs/Gameplay/dungeon-themed-routes-20261001.md`。

返回主场景：

```text
open /Game/GameMaps/DayNight_Lighting
```

新房间须使用自己的已保存地图路径；以上是当前案例，不是所有房间共用入口。

## 统一翻越制作合同

- 共用 `Source/FPSGAME/Movement/FPSTraversalComponent` 和 `FPSTraversalRules`，以空格和真实碰撞判定翻越/攀爬。不要为每个房间、每根栏杆复制交互代码或增加位置特判。
- 普通稳定障碍沿用通用判定。需要双向跨栏、台阶落点和高处翻下的栏杆，在 Actor 或组件上设置 `Traversal.GuardrailDrop`；此标记不是所有家具、墙体的默认标签。
- 标记不会生成碰撞。栏杆需有与轮廓吻合的连续简单碰撞和可抓顶部；双向阻挡 Pawn，保持查询碰撞。可参考净化站的分段 UCX 与 `UseSimpleAndComplex`。斜栏杆碰撞跟随坡度，扶手与立柱连接，不能只依赖没有连续阻挡体积的细管外观。
- 楼梯、平台、柜体应提供真实承托面；角色两侧接近位置、落点、头部空间和完整胶囊路线都要留净空。家具贴墙不能占满玩家通路，不能靠交互代码穿过实际障碍。
- 作者模块零件写 `guardrail_drop: true`，由 `Dungeons/AuthoredDungeonGenerator` 生成带同一标签的组件；这类零件保留独立交互组件，不并入丢失标记语义的普通静态实例批次。独立样板和正式随机模块使用相同碰撞及标签。
- 当前能力：站立低翻越上限 120 cm、攀爬抓取上限 200 cm；空中抓取以当前胶囊脚底为参考，障碍深度上限 120 cm。专用栏杆允许已查询落点向下最多 300 cm，落点台阶起伏受 CharacterMovement 的正常踏步高度限制。较高栏杆需先跳起/接近，不代表从任意地面高度都能跨过。
- 2026-10-01 修正已支持外侧较高栏杆探测、栏杆背面台阶落点、镂空踏步的实际胶囊支撑；内侧翻下保留。它解决共用判定缺口，不免除新资产的碰撞与布局制作。异常资产优先修其几何、碰撞或标签；只有通用判定确有缺口时再改共用代码。
- 普通浅柜顶的 Mantle 已将脚下承托与身体净空分开：九点承托半径为角色胶囊半径的一半，并有限搜索顶部落脚位置；身体胶囊尺寸及整段碰撞扫掠不缩小。后续同类柜体沿用此规则，无需添加栏杆标签或人为加大碰撞体。实现与未测试边界见工程 `Docs/Gameplay/traversal-shallow-top-footing-20261001.md`。

源码及构建记录见工程 `Docs/Gameplay/flue-gas-rail-two-way-traversal-20261001.md` 和
`SourceAssets/DungeonFlueGasStation20261001/RailTraversal20261001/Receipts/completion.json`。

## 用户确认、正式接入、清理样板

- 用户负责体验和确认。仅询问修复状态、要求预览命令，或构建成功，都不表示样板已通过；“确认后清理”不是立即删除当前预览地图。
- 用户确认可用并进入正式接入阶段后，完成房间目录、端口/cells、碰撞、交互标签、灯光调度、遭遇锚点与必要资产引用落盘。固定主题组合遵守用户已定顺序，不因增加过渡间拆散组合。
- 在正式使用者已引用所需资产后，同一次收尾执行已授权的样板退役，不需要用户再次提醒“删测试场景”。接入尚未完成或用户仍需预览时保留样板，说明当前阶段。
- 清理临时 `.umap` 及其专属外部 Actor/对象、封口板、预览出生点/返回门、预览专用菜单或祭坛入口、临时 `MapsToCook` 和只用于样板的安装入口。仅处理本次样板专属内容，不批量删除 `Design` 目录，也不移除共用交互类。
- 保留正式场景共享的网格、材质、贴图、灯具、模块配置，以及 Blender 源文件和可用生产导入脚本。共享资产的归属/引用读取属于安全清理所需资料，不扩展为默认全项目审计。
- 按项目归档规则将退役文件移入 `trash/<task>/`，记录原路径、归档路径、大小、SHA-256、原因和保留替代物；移除正式目录引用。停止/归档样板重建入口，避免下一次作者重建又恢复临时地图或菜单。
- 有活编辑器持有目标包时，按既有桥的批次互斥处理；不在外部覆盖已加载或未保存资产。无法安全清理的具体文件如实列出，不以“已写清理脚本”冒充清理完成。
- 收尾明确正式接入和样板清理各自状态，以及是否由用户实测。该流程不自动授权运行测试、启动游戏或验收渲染。
