# 手枪握把砸击：程序化尝试 → 作者源 clip（2026-09-17 未获认可；V3–V8 程序化排查；V9 改走作者源）

单持手枪的快速进战近战：松开左手、右手持枪以握把向前猛砸。V3 实测仍「模型不见了」且左手食指上伸被否；V4 定位到贯穿 V1 起的快照棘轮漂移（火球分支逐帧清零共享快照）并按用户定义重做左手；**用户指定实测枪为 Dan Wesson 715**，V4 判定仍不达标；V5 把「标量常量 + 分段公式」换成关键帧表（0.60s 六段、肘极/肩线驱动、左手松握、命中与画面同源）；V6 修掉姿态层自激振荡；**V7 定位到枪体消失的真因——武器搬运的中间变换丢了 100 倍骨缩放**，修复后用户实机看到枪全程在手里、左手自然下垂。实现入口 `Skills/FPSQuickCombatComponent.*`、`Skills/QuickCombatPistolMotion.h`、`FPSCastingMeshComponent::ApplyQuickCombatPose`；案例与数值见 `Docs/Skills/quick-combat-placeholder-20260917.md`。本页记录可复用的机制结论与未解决项，不把未验收状态写成可用功能。

## 可复用的机制结论

- 双臂+武器组的入场快照与局部混合沿用火球模式：链骨走向两骨 IK 解（恒骨长、93% 肩带支撑、前臂继承掌侧 roll 的闭式解），手指/子骨按类别跟随。**锁骨不是「保持动画驱动」就够**：需要肩带跟随时，上臂根必须由锁骨尾端解出（`RefUpperHeadInClav = 锁骨⁻¹·上臂根`），锁骨偏航/位移与上臂根同源；够不到臂长时**锁骨与上臂根一起**前送，只推上臂根会让肩部脱节（V4 的左肩问题）。
- **挥击感来自肘极与肩线，不来自腕部自转**：只有「入场→蓄势→接触」三个位姿 + 线性/二次插值，得到的是手在平移、枪在手里转。V5 给每个关键帧加了肘极向量（蓄势：外后上 → 下砸：前下）与肩线偏航（正 = 右肩前送），腕只作 IK 目标。
- **关键帧表优于标量常量**：V1–V4 的 `CockTiltDeg/ContactTiltDeg/±偏移` 是在画面不正确（枪飞 + 手腕扭断）的前提下盲调的，数值本身没有意义。把每条通道摊成时间轴上的键（含分段缓动）后，调参是改表而不是改公式，也才可能按参考对齐节拍。
- 视模武器不挂在手骨链下时，脱手/砸击类动作需把武器组当刚体搬运：目标 = 「目标手 × 入场手⁻¹」差值作用到入场武器根，再**一次性**转回网格空间。乘法顺序或空间转换错一次，武器每帧吃一个垃圾变换直接飞出视模——本案实际发生的失败，位置在 `ApplyQuickCombatPose` 的武器搬运段，已修未验。
- **共享入场快照的清零权只属于「无人占用」态**：火球/砸击两个姿态分支曾各写各的 `EntrySerial=0`，砸击期间火球分支每帧清零→砸击分支每帧重捕快照→目标相对移动基线棘轮式漂移，几帧内模型飞出视模。本案「枪飞」从 V1 起的真正根因是它（搬运乘序与旋转前乘两度「修复」都没用，因为基线在动）。多动作共享一份快照时，清零必须收敛到「所有动作都不占用」的单一出口。
- **相机空间旋转要前乘**：`FQuat(轴,θ)*EntryHand.GetRotation()` 是绕相机轴转整只手；写成后乘 `EntryHand.GetRotation()*FQuat(轴,θ)` 会绕手骨局部轴扭腕。本案 V1/V2 的「上仰竖枪」注释写绕相机右轴、代码却后乘，与枪飞 bug 叠加从未被看到，2026-09-18 才修复（两手同修）。写空间旋转先问「轴在谁的坐标系」。
- 左手手指张开度借用火球手型配置的做法**在本案被否**：枪模 rigs 上呈现为食指向上伸开的怪姿态；且用户定义的左手行为是「松握→自然下垂移出镜头→攻击后回握」，与参考视频的开掌前推不同。V5 的松握改为**手指子骨向参考姿势混合最多 30%**（`LeftRelax` 关键帧）——轴向无关、不会出现单指伸直，同时不再冻结手腕朝向（下垂方向给左手朝向关键帧）。参考视频只对右臂动作语言有效。
- WPN 组挂接关系（挂手/挂骨架根）须运行时检测，不能假设 M1911 与 715 骨架一致；两种情况分别对应「手腕自然带动」与「整组差值搬运」两条路径。
- 近战打击感约一半来自镜头：程序化动作若没有相机语言（蓄势随动+接触冲量），手臂层再准也「不像」。本案 V3 补上了 `GetCameraMotion`（配重锤 exp·sin 冲量家族，方向改下压），此前 V1/V2 完全没接。
- **命中判定必须与画面同源**：V4 前是从眼位沿视线向前 2m 的球扫，视觉打击点却在手下方 14cm、前方 18cm——「打到了但没打到」。V5 改由 `GetQuickCombatStrikeProbe()` 给出握把底世界位置，方向取「玩家瞄准 65% + 挥击走向 35%」加权，长度仍用技能 `rangeCM`。
- 多个动作共用一份快照时，序号也要分段：`EntrySerial` 被火球与砸击共用，砸击动作号可能与火球动作号撞值，导致砸击首帧沿用上一个动作的快照。V5 用 `0x40000000` 序号段隔离。
- **程序化姿态层不能回读「当前姿态数组」**：组件空间的骨骼数组里留着本层上一帧写回的结果（FinalizeBoneTransform 的写入就在这个数组里），拿它当下一帧输入——肘极取当前肘位、收势混合取当前局部姿态——就会逐帧放大成自激。本案实测：同一动作 `t=0.39` 正常，`t=0.44` 起爆到 162→347→1150cm，武器距右手最大 1300cm。**一律只用「入场快照 + 关键帧目标」，组装写成「入场绝对姿态 → 目标绝对姿态」的绝对混合**，就没有任何反馈路径。
- **「枪看不见」要先量骨缩放，再怀疑包围盒**：这把枪的网格导入后手骨/武器骨**运行时是 100 倍缩放**（`右腕缩放=100.00/参考100.00`，而引擎 `Skeleton` 资产的参考姿势读出来是 1——两者不一致，别看错来源）。武器搬运若写成 `FTransform(旋转, 位置)`（缩放默认 1），`HandDeltaCam` 缩放会变成 1/100、搬运结果缩放=1 → **枪体缩到 1/100 等效消失，而挂骨配件/激光射线照常显示**，看起来像"只剩配件"。**规则：任何由本层重建的骨骼变换都要显式带上入场缩放**（手部基准、武器目标、手臂链骨）。自检日志打印 `入场缩放/参考缩放/当前缩放` 可直接判定。
- **刚体搬运的乘法顺序（引擎语义，别再凭直觉）**：`Core/Math/TransformNonVectorized.h` 的 `Multiply` 规定 `C=A*B` ⇒ `C.T=B.T+B.Q*(B.S*A.T)`、`C.Q=B.Q*A.Q`（**右操作数=父级/外层**），`GetRelativeTransform(Other)=this*Other⁻¹`。所以本工程里 `Child_abs=Child_local*Parent_abs`、`Local=Child_abs*Parent_abs⁻¹` 一致成立；而**把物体 A 按「另一物体 B 的自身帧差值」搬运**要写
  `Rel = A_entry * B_entry⁻¹; A_goal = Rel * B_goal`。
  本案 V7 写成 `B_goal*B_entry⁻¹*A_entry`（差值套在外层）→ 不是刚体变换：**枪相对手漂移、朝向错位**（实测 `武器距右手` 从 13.0 漂到 16.9）。判据：刚体搬运下该距离必须**全程恒定**。
- **视模剔除是另一条独立路径，不要与缩放混淆**：新姿态若超出「为旧动目标定的导入包围盒」，UE 会整块剔除视模，骨骼位置日志同样正常（先例 `Docs/Weapons/m1911-development-audit-20260913.md` 第 1 行：M1911 `BoundsScale=4.17` 就是这么定的）。但本案实测：把包围盒放大到 13 米包络后枪依旧不可见 ⇒ **剔除不是本症状的成因**，那段放大/跟随姿态骨的改动已整段删除。排查顺序：先看缩放 → 再看分区可见性 → 最后才是包围盒。

## 结论：这类动作应当走作者源，不要写程序化姿态层（2026-09-18 V9）

用户决定并已执行：把 715 的握把砸击做成**作者源单发 clip**（`SourceAssets/DanWesson715QuickCombat20260918`），
沿用这把枪换弹的约定——**把持枪运动烘焙到 `WPN_root`、由枪带动右手**（`hand_at(p, idle, 'r', G @ RIGHT_GRIP)`），
左手用同一解算器做松握→下垂出镜→回握；逐帧 120 Hz 烘焙，0.60s、接触 0.30s。

为什么改：
- 程序化路线 V6/V7/V8 修的三个根因（回读被自己写脏的姿态数组导致自激、重建变换丢 100 倍骨缩放、搬运不写成刚体形式）
  **都是这条路线自带的**，不是写错代码；每修一次都要动共享引擎代码、重链 DLL、还要跟并行会话的编译冲突抢编译窗口。
- 作者源路线把这些问题变成构造问题：枪的运动在 `WPN_root` 上，右手由握把关系解算，
  `|WPN_root − hand_r|` 全程恒定（本案 0.133 m），**"不跟手/漂移"不可能出现**；缩放由骨架自带，不再由本层重建。
- 代价是每轮要实机反馈（像 ASH-12 五轮那样），收益是改的是资产、不动引擎代码。

适用判断：**动作本体是"固定编排"（近战一击、换弹、开镜等）→ 作者源 clip**；
只有"跟玩家状态实时耦合"的部分（施法凝聚/脱手、格挡受击、攀爬接触）才留程序化层。
程序化层若仍要做，先量三件事：骨缩放（本 rig 运行时 100 倍）、组件空间数组的可信来源、搬运的相对不变量。

## 未解决（下次开发入口）

### 打击感通道清单（2026-09-18 V10：拿已接受的近战动作当基准逐通道对齐）

做近战打击感时不要只调摄像机冲量；按**已获接受的同类动作**（本案＝符文剑配重锤）逐通道核对：

| 通道 | 说明 |
| --- | --- |
| 动作本体 | 固定编排走作者源 clip；接触处给 2–3 帧保持（顿帧做在 clip 里，不动引擎时钟） |
| 命中确认 | `AFPSGAMECharacter::NotifyConfirmedWeaponHit(Target,Applied,&DamageResult,bFirearmHit=false)`：准星命中标记 + 钝器确认音 + 怪物血条反馈；**近战/技能必须自己调**，枪械走落点通道 |
| 命中音 / 挥动音 | 命中音按武器；挥动层用近战攻击层（本项目唯一挥动音源 `S_Sword_Attack`） |
| 动作镜头 | 跟随动作阶段（蓄势/前送/跟随回位），与命中冲量分两层 |
| 命中冲量 | `exp·sin` 阻尼族；**量级要对比已接受动作的"有效"值**（配重锤基础值还要 ×`SwordCameraStrength=1.5`），否则新动作会明显偏弱 |
| 敌方反应 | 击退/眩晕（`ReceiveStun`）等既有通道，数值改动属于平衡，不在打击感改动里顺手改 |

本案补齐的三处缺口：命中确认完全没调（无准星标记/确认音/血条反馈）、动作镜头只剩命中冲量（V9 删程序化层时一并丢了）、
命中冲量比配重锤弱一半以上。
