# FPSGAME 场景开发标准

## 从设计图到关卡搭建

**设计图 → 组件三视图 → 模型 → UE 搭建**。2026-11-13，用户确认温带丘陵旧教堂的制作方式可作为建筑与地编布局的标准工作流。新建地标、可进入建筑或成组布景时沿用这条顺序；局部改版从受影响的阶段接续。

1. **设计图定布局。** 先从玩家主要来路画整体外景，定主体轮廓、入口、道路和地形的关系。可进入的建筑再画室内，从入口看向主要空间，定通道、陈设与采光方向。用带尺寸的平面和必要立面把内外两张图对齐，明确开间、地坪标高、门窗位置和玩家净空。
2. **拆件，再做三视图。** 根据设计图列资产清单，逐件标明编号、用途、目标宽深高（cm）、数量、朝向、枢轴和拼接或安装面，并注明项目复用、定尺建模或多视图生成。需生成的构件各出同一物件、同一比例的三张正交单图。常用正、侧、背视；顶部决定造型时改用顶视。门扇与门套等配合件共用洞口尺寸，能活动的部分单独拆件。
3. **按清单制作模型。** 特色构件以每件的三张独立图作为同一次多视图生成的输入；旧教堂使用 Meshy。墙段、洞口、楼地面、屋面等有连续拼缝的结构按尺寸建模。整理生成件的实际尺度、朝向、支承面、材质和碰撞，再导入 UE。资产编号贯穿三视图、模型和摆放清单，同款重复件复用同一网格。 原因：不同生成分支的输入和采样器合同不同，混接并不会自动形成可用的多视图流程。
4. **按设计图搭建目标关卡。** 先用共同的局部原点、入口中轴和地坪标高定主体，再放门窗、装饰和交互件。按整体图收地基、道路与植被边缘，按室内图安排家具、通行和窗光。需要整体缩放时，一并调整门槛、踏步、挂点和场地衔接。布局或材质改动写回对应模块和摆放配置，确保以后重建能沿用。 原因：明确目标后才能复用正确的既有入口，准备步骤不应扩大已授权工作的边界。

旧教堂可直接对照整体内外景、建筑平立面、构件三视图和尺寸清单。钟墙与石门套走 Meshy，墙身和真实门洞按尺寸制作，青铜火把复用项目资产。该案例的主体内外墙最终统一为一种扫描石材，以法线和高度表现石缝。旧教堂设计与资产清单（本机资料：`SourceAssets/TemperateHillsOldChapel/Concept01/设计与资产清单.md`，不随本次发布）

## 制作与预览

以下约定由用户于 2026-10-01 确定，适用于新房间、楼梯、平台及独立场景主体样板。已有地图内的地标沿用目标地图的搭建入口。

1. 使用当前工程 `D:/FPS3D/FPSGAME`。复用已认可的模型、材质、灯光和交互；规则结构按实际尺寸制作。作者配置、可编辑源、导出物和正式资产分别保留。 原因：用户认可的是具体母版和观感，换成另一版本会改变已有接触或外观基线。
2. 主体阶段独立保存 `/Game/GameMaps/Design/L_<Room>_Subject`，配置正常 FPS GameMode、有效 PlayerStart、连续可走地面和必要碰撞。尚未认可的样板不提前加入随机池。
3. 默认通过游戏控制台 `open <完整地图包路径>` 进入，交付具体命令。无需新增祭坛出征菜单项、正式传送入口或专用 C++ 入口。地图包路径不含 `.umap`，不凭文件显示名猜路径。 原因：文件名与版本标签不能证明正在使用的对象，制作需要对应实际引用的资源身份。
4. 预览方式以本机编辑器/开发运行内容为默认。只有用户要求在打包游戏中预览，才把需要的样板加入临时烹饪清单；控制台命令不能加载未烹饪地图。不把所有临时样板永久加入 `MapsToCook`。 原因：打包程序只能加载已烹饪资源，临时预览需求也不应永久扩大正式 cook 清单。
5. 交付必要的返回主场景命令；场景已有返回传送门可在预览阶段保留，但正式模块不带它。预览期间不改主场景默认地图。 原因：预览需要可返回的路径，但临时传送门和默认地图不属于正式模块的组成部分。
6. 继续遵守后台制作、必要构建/导入/保存、不主动打开编辑器、不主动测试的约定。控制台命令交给用户执行，不因交付命令而自行进入游戏或截图。 原因：制作授权不包含额外运行或验收，交付应保留未测试的实际状态。

净化站与货运仓库均已获用户确认，已接入三条固定主题路线并归档样板。仓库的主体、精修资产、拖车、灯光与栏杆交互随正式模块保留；旧样板地图及直达命令已退役。

正式随机地牢为 `/Game/GameMaps/L_Dungeon_Randomized`。主题内部顺序固定，基础设施房只在组合前后补充；三路汇流后进入数据档案中心，再通往 Boss。任意一路清理完毕并清理档案中心即可开启 Boss 通路。制作与未测试边界见工程 `Docs/Gameplay/dungeon-themed-routes-20261001.md`。 原因：任务进度与场景实例有独立身份，目标显示和权威开门必须对应同一轮任务。

返回主场景：

```text
open /Game/GameMaps/DayNight_Lighting
```

新房间须使用自己的已保存地图路径；以上是当前案例，不是所有房间共用入口。

## 场景照明标准（2026-10-13）

向下照明的吊灯、吸顶灯和廊下灯不得向上直射天花板。光源逐盏匹配灯具出光面，以实际生成组件的世界 +X 方向为准；不能只看配方旋转或通过整体降亮掩盖方向错误。UE 原生灯创建后先设置 Movable，再设置完整世界姿态，避免默认根旋转叠加及游戏世界拒绝移动。

保留已认可吊灯效果，一楼廊下、主入口、楼梯及四角由本层灯具保证最低可读照明；闪烁和坏灯不独自承担通路基础照明。亮度、射程、光锥和楼板遮挡分别处理，不能让二楼灯穿楼板补一楼。配方、运行时创建、地图保存、性能约束及证据边界统一见 [灯具与照明层次标准](fixture-lighting-standard.md)。 原因：用户认可的是具体母版和观感，换成另一版本会改变已有接触或外观基线。

## 统一翻越制作合同

- 共用 `Source/FPSGAME/Movement/FPSTraversalComponent` 和 `FPSTraversalRules`，以空格和真实碰撞判定翻越/攀爬。不要为每个房间、每根栏杆复制交互代码或增加位置特判。 原因：移动状态需要真实支撑和碰撞条件，达到缓存坐标并不等于动作已经安全完成。
- 普通稳定障碍沿用通用判定。需要双向跨栏、台阶落点和高处翻下的栏杆，在 Actor 或组件上设置 `Traversal.GuardrailDrop`；此标记不是所有家具、墙体的默认标签。
- 标记不会生成碰撞。栏杆需有与轮廓吻合的连续简单碰撞和可抓顶部；双向阻挡 Pawn，保持查询碰撞。可参考净化站的分段 UCX 与 `UseSimpleAndComplex`。斜栏杆碰撞跟随坡度，扶手与立柱连接，不能只依赖没有连续阻挡体积的细管外观。 原因：动作需要持续接触实际武器或道具，只有骨骼位置接近并不能保证真实表面贴合。
- 楼梯、平台、柜体应提供真实承托面；角色两侧接近位置、落点、头部空间和完整胶囊路线都要留净空。家具贴墙不能占满玩家通路，不能靠交互代码穿过实际障碍。
- 作者模块零件写 `guardrail_drop: true`，由 `Dungeons/AuthoredDungeonGenerator` 生成带同一标签的组件；这类零件保留独立交互组件，不并入丢失标记语义的普通静态实例批次。独立样板和正式随机模块使用相同碰撞及标签。
- 当前能力：站立低翻越上限 120 cm、攀爬抓取上限 200 cm；空中抓取以当前胶囊脚底为参考，障碍深度上限 120 cm。专用栏杆允许已查询落点向下最多 300 cm，落点台阶起伏受 CharacterMovement 的正常踏步高度限制。较高栏杆需先跳起/接近，不代表从任意地面高度都能跨过。
- 2026-10-01 修正已支持外侧较高栏杆探测、栏杆背面台阶落点、镂空踏步的实际胶囊支撑；内侧翻下保留。它解决共用判定缺口，不免除新资产的碰撞与布局制作。异常资产优先修其几何、碰撞或标签；只有通用判定确有缺口时再改共用代码。 原因：移动状态需要真实支撑和碰撞条件，达到缓存坐标并不等于动作已经安全完成。
- 普通浅柜顶的 Mantle 已将脚下承托与身体净空分开：九点承托半径为角色胶囊半径的一半，并有限搜索顶部落脚位置；身体胶囊尺寸及整段碰撞扫掠不缩小。后续同类柜体沿用此规则，无需添加栏杆标签或人为加大碰撞体。实现与未测试边界见工程 `Docs/Gameplay/traversal-shallow-top-footing-20261001.md`。 原因：刷怪和寻路必须使用相容的身体尺寸，否则可生成的位置未必能够通行。

源码及构建记录见工程 `Docs/Gameplay/flue-gas-rail-two-way-traversal-20261001.md` 和
`SourceAssets/DungeonFlueGasStation20261001/RailTraversal20261001/Receipts/completion.json`。
记录是制作/构建证据，不是用户实测通过。

## 用户确认、正式接入、清理样板

- 用户负责体验和确认。仅询问修复状态、要求预览命令，或构建成功，都不表示样板已通过；“确认后清理”不是立即删除当前预览地图。
- 用户确认可用并进入正式接入阶段后，完成房间目录、端口/cells、碰撞、交互标签、灯光调度、遭遇锚点与必要资产引用落盘。固定主题组合遵守用户已定顺序，不因增加过渡间拆散组合。
- 在正式使用者已引用所需资产后，同一次收尾执行已授权的样板退役，不需要用户再次提醒“删测试场景”。接入尚未完成或用户仍需预览时保留样板，说明当前阶段。
- 清理临时 `.umap` 及其专属外部 Actor/对象、封口板、预览出生点/返回门、预览专用菜单或祭坛入口、临时 `MapsToCook` 和只用于样板的安装入口。仅处理本次样板专属内容，不批量删除 `Design` 目录，也不移除共用交互类。 原因：样板专属入口与共用场景能力归属不同，精确清理可移除临时内容并保留正式场景依赖。
- 保留正式场景共享的网格、材质、贴图、灯具、模块配置，以及 Blender 源文件和可用生产导入脚本。共享资产的归属/引用读取属于安全清理所需资料，不扩展为默认全项目审计。 原因：样板可以退役而共用素材仍在生产使用，清理需要保留实际依赖及其作者入口。
- 按项目归档规则将退役文件移入 `trash/<task>/`，记录原路径、归档路径、大小、SHA-256、原因和保留替代物；移除正式目录引用。停止/归档样板重建入口，避免下一次作者重建又恢复临时地图或菜单。
- 有活编辑器持有目标包时，按既有桥的批次互斥处理；不在外部覆盖已加载或未保存资产。无法安全清理的具体文件如实列出，不以“已写清理脚本”冒充清理完成。
- 收尾明确正式接入和样板清理各自状态，以及是否由用户实测。该流程不自动授权运行测试、启动游戏或验收渲染。 原因：制作授权不包含额外运行或验收，交付应保留未测试的实际状态。

### 用户明确保留的线路测试图

用户要求留作后续怪物生成或继续调整时，主题获认可后仍保留该线路测试地图、重建脚本和布局配置，不套用默认样板退役条款。正式引用与保留测试用途分别记录，保留测试图不自动改变默认地图、烹饪清单或怪物生成。 原因：用户指定保留的样板仍有后续用途，不能按通用退役规则删除，也不能因此自动接入正式玩法。

连续线路样板按完整房体的三维占位和真实门位连接，不只用外部入口间距累加偏移。侧翼、地下空间、上层观察台、栏杆及楼梯口都包含在占位中；邻房侧翼侵入楼梯口时，先修房间间距和走廊连接，不能按截图删除被侵入房间的有效结构。独立房体局部坐标及正式求解器的 cells 保持一致。 原因：入口间距不代表完整房体边界，忽略侧翼和高差会让相邻有效结构互相侵入。

采用版本接入从最新已保存生成器目录增量合并，只修改本主题的容器组、专属宝箱和核心顺序；同时保存资产硬引用，保留其他主题、遭遇和门闸规则。作者镜像同步采用相同范围，旧构建链末端重放本主题扩展；只有真实导入/地图保存回执才激活该扩展。案例见 `SourceAssets/DungeonTreatmentTheme20261003`。
