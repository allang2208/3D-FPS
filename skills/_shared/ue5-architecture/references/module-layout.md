# 模块边界参考

- 按现有工程划分 Runtime、Editor 与公开接口，不为一次类修改强制新增模块。原因：模块是依赖和打包边界，数量本身不等于更清晰的结构。
- 运行目标不依赖仅编辑器可用的模块；编辑器扩展放在现有 Editor 目标或受正确条件保护的入口。原因：编辑器环境的能力未必能进入 Game 或 Shipping 目标。
- Public 只暴露消费者需要的合同，具体实现和非导出类型留在 Private。原因：公开包含关系会传播编译依赖和接口耦合。
- 先按实际调用确定数据、运行系统与 UI 的依赖方向，禁止形成模块循环。原因：接口层级要匹配真实所有权，抽象的“上层/下层”名称不能消除循环引用。

常见职责包括数据定义、Actor/Component/Subsystem、UMG/Slate 显示和编辑器工具；这些是定位分类，不要求为每类新建独立模块。 原因：这些是职责分类而非强制工程结构，实际拆分应由依赖与复用边界决定，避免制造没有独立职责的模块。

## 保持行为的清理与长文件拆分

- 先列功能边界、入口和精确路径；超过约定行数的文件先给拆分方案，按已获授权范围实施。原因：行数用于提示复杂度，不能替代职责划分或扩大清理范围。
- 只复用输入、返回、读取顺序和副作用时点相同的逻辑；一行包装若增加归属或参数转发则保留原式。原因：文本相似不等于行为等价，抽象本身也有维护成本。
- 长文件按完整职责移动，内部共享类型只声明一处，状态实例、静态初始化和 CVar 归属保持。原因：同名复制或改变初始化位置会引入额外状态和生命周期差异。
- 连续生成数组按作者已有家族拆分时同步作者输出；不按固定行数切成 include 碎片。原因：消费者按帧、骨骼和变体读取，机械分块会增加新的索引合同。
- UFUNCTION/RPC、反射字段、诊断分支及旧作者输入不能只因缺少手写调用而删除。原因：生成注册、资产或恢复链可能仍是有效调用者。
- 清理完成与有理由保留分别记录；必要构建仍等待共享占用，不抢锁、不终止其他进程。原因：保留项不是已删除成果，构建也不能破坏并行工作的状态。
