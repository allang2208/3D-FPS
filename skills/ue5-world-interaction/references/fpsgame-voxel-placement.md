# FPSGAME 体素建造的放置交互（2026-09-16）

适用于 FPSGAME 单人 20 cm 体素建造（`Source/FPSGAME/Building/`，数值与存档标准见 `Docs/Building/voxel-build-workflow.md`）。这里是交互层的可迁移规则，同样适用于其他"网格吸附 + 幽灵预览"的建造系统。

## 状态机

- 一条输入键循环三层状态：不在建造 → 建造 + 抽屉（鼠标 / `FInputModeUIOnly`）→ 建造 + 瞄准（游戏输入）。抽屉开着才给光标；回到瞄准必须恢复 `FInputModeGameOnly`，否则视角输入被吞。
- 退出建造的路径不止一条：自己按键、打开别的菜单、外部 UI 抢走光标、关卡切换、Live Coding 重载。清理逻辑挂在按键那一条路上就一定会漏。

## 幽灵预览与高亮

- 预览用独立 `RF_Transient` Actor（Owner = 玩家控制器）：`AController` 默认不可见，挂在它上面的组件单靠 `SetVisibility` 不会显示。
- 高亮组件（金色轮廓用 `UInstancedStaticMeshComponent`）离开模式时必须**同时**清实例 + 关可见性 + 复位"上次重建签名"缓存。只关可见性会留下实例缓冲；只清实例而不复位签名，下一帧会因判定"无变化"而不重建。
- 高亮组件的指针不要只放在文件级 `static` 里：模块重载（Live Coding）会把它复位，指向已销毁组件的指针静默失联，正在显示的实例缓冲再也没人清。缓存为空时**按名字从宿主 Actor 重新解析**，宿主用 `UPROPERTY` 持有。
- 兜底：不在该模式时每帧检查一次"组件可见或实例数 > 0"就清一次，成本是一次可见性查询。

## 材质与实例化静态网格

- 挂在 `UInstancedStaticMeshComponent` 上的材质必须打开 **Used with Instanced Static Meshes** 使用标记；缺标记时引擎**静默**改用默认材质，表现为"改了材质却没变化"，只在日志里留一行提示。
- Unlit + Emissive 的自发光量约 1.0 在白天场景里读起来是暗灰；要让金色真的发亮需要推到 HDR 区间（1.2–3.6）并按时间脉动。

## 每帧开销的取舍

- 只节流贵的那部分（地形采样 20 Hz、方案校验按变化）；**幽灵跟随和高亮可见性必须每帧**，否则表现成"预览间歇性消失"和"跟手性差"。
- 每个提前 `return` 的分支都要自己保住状态。不要在函数入口统一 `Reset()` 计划与可用性：被跳过的帧会把上一次的方案连同"可放置"标志一起清掉，表现为"点着没反应"。
- 缓存签名要真的能命中：若入口每帧把缓存的格子 ID 复位成 `MAX_int32`，那么"只在变化时重建"的判断永远命不中，实例缓冲会每帧重建。

## 吸附与自由放置

- 吸附模式要"粘住表面"：中心射线没命中时，用 8 方向 × 1.5°/3° 的锥形辅助射线找最近的可见体素；只有锥内完全没有体素才回退到空气位置。否则镜头稍偏，预览就跳到空中。
- 自由放置（取消吸附）必须**完全跟随**瞄准，连续位置、每帧更新，不要复用吸附方案或沿用节流。
- 向上建造要单独定规则：视线仰角超过阈值时瞄准侧面 → 在目标格正上方叠层；否则 2 m 以上（眼高）的墙顶永远瞄不到，会被误判成"数值上限"。

## 症状 → 先查什么

| 症状 | 先查 |
| --- | --- |
| 退出模式后高亮轮廓还在 | 组件指针是否还在（热补丁复位 static）、是否清实例、是否有每帧兜底清理 |
| 高亮颜色不对、像没生效 | 实例化静态网格的材质使用标记；Emissive 是否在 HDR 区间 |
| 夹角或相邻位置高亮缺失 | 边框是否被埋进邻居格：只画朝向空处的边 |
| 预览间歇性消失 / 点击无效 | 被节流跳过的帧是否清空了方案与可用性 |
| 镜头稍偏预览就跳到空中 | 缺少锥形吸附辅助 |
| 建造失败时整栋跟着塌 | 求解结果是否只按"最新那批新增格"过滤，见 `Docs/Building/voxel-build-workflow.md` 3.6 |

## 预制件（prefab）：预览与落地必须同口径（2026-09-17）

"先看幽灵、再点击生成"的对象一旦预览与生成用了两套摆放公式，就必然出现"预览在这儿、造出来在那儿"。
FPSGAME 里这对入口只有两处，**必须成对修改**：`UVoxelBuildComponent::UpdatePrefabPreview()`（预览）与
`AVoxelBuildWorld::SpawnPrefab()`（生成）。判据写在 `Docs/Building/voxel-build-workflow.md` 3.8。

- **分流条件看构件类型，不要看字段是否为空**。2026-09-17 的事故就是 `SpawnPrefab()` 按 `Mesh` 是否为空分流：
  门这类"逻辑构件"也要填 `Mesh`（只用于抽屉缩略图），于是走了普通构件的居中口径，落地比预览高了一个半身高（门高 200 cm）。
- **按包围盒摆放，不要按 pivot**。第三方/StarterContent 网格的 pivot 常在边界（门框在底边、门板在角上）。
  统一 `FBoxSphereBounds`：位置 = 目标中心 − `Origin`，贴地再加 `BoxExtent.Z`（`AColdSteelDoor::AlignGeometry()` 是参考实现）。
- **同格对照**是验收动作：同一占格里预览／落地各放一次，目视两者的包围盒是否重合；预览网格比落地外形小一圈（如门板 vs 门框）允许 5–15 cm 轮廓差，不允许整体差半个身位。
- 逻辑构件的完整契约（`ActorClass`／`ActorOffsetCm`、材质整体替换、拆除沿挂载链解析）见
  `Docs/Building/voxel-build-workflow.md` 5.1。

## 可动构件（门／窗）与构件支撑（2026-09-18）

同一套 20 cm 体素建造里的**逻辑构件**（自带 Actor 的门、窗、双开门）除了"预览＝落地"之外，还有几条口径：

- **占格必须是 20 cm 的整数倍**：判据是**网格包围盒逐轴能被 20 整除**。包里 StarterContent 的门是
  24.8 × 114 × 212 cm，高度 212 卡在 10 格（200）与 11 格（220）之间，砌墙时对不齐——这就是用户说的"高度突出"。
  门窗这类**要人走的洞口必须整除**；只有"网格略小于占格"的装饰件才允许向上取整占格。
  同族件（100×100 窗 / 2×2 m 双开门 / 单扇门）都登记三档材质（wood／stone／marble 各一条，`Material` 分组决定进哪栏）。
- **铰链贴扇面，不要放在框进深中间**：窗扇若绕"框进深中点"转，90° 时靠铰链的半个板厚会切进窗框边梃。
  正确做法是铰链贴在扇的外侧面（向外开）或内侧面（向内开），扇相对铰链反向偏移（换向时扇的世界位置不变）；
  被挡反向的检测也要按**候选开向**摆检测盒，否则换向判定偏一个贴面差。
- **多扇件用子类共享逻辑**：`AColdSteelDoubleDoor : AColdSteelWindow` 只换网格与三个数值（边梃宽、板厚一半、
  自动关秒数），把基类的几何常量提到 `protected` 即可——开合、被挡反向、玩家不参与阻塞、整体换材质、支撑判定全部零重复。
  再加同族件（推拉门、活板、百叶）照这条路走。
- **把手的镜像侧跟着模型走**：`AColdSteelWindow` 的约定是"把手在网格 +Y 侧"，右扇转 180° 让把手朝中缝；
  换成**包里的门扇**（门把在网格 **−Y** 侧）有两条等价做法：① 改成**左扇**转 180°（动两行 C++）；
  ② 烘焙时**把门扇网格绕 Z 转 180°**，让把手落到 +Y，C++ 一行不用改（2026-09-18 第二轮双开门采用这条）。
  贯通把手还占摆向那一侧：开角要留余量（85°；92° 时把手尖会扫进门框约 4 cm）。
- **构件必须有"着落"**（否则拆掉周围方块后构件悬空浮着——用户报过）：三条任一成立即可——① 底面下有地形
  （与体素共用 `VoxelGrounding` 的地面锚定口径）；② 任一占格与体素面对面相邻；③ 任一占格与**另一件构件**相邻
  （叠放件靠这条）。`CanPlacePrefab()` 悬空直接拒绝放置；`VerifyPrefabSupport()` 挂在 **`ApplyChanges()`** 末尾——
  那是所有体素增减（玩家编辑、过载压坏、爆炸摧毁、倒塌脱落）的唯一汇合点，构件才会跟着墙一起掉。
  实现上只筛"改动点一格以内"命中的构件（占格 → 锚格的映射），大件按格抽样（凉亭一件 8.7 万格）。

## 调整已有构件的尺寸：先只改网格（2026-09-18 回退事故）

那一轮为了把包里的门缩放到网格尺寸，顺手重写了 `AColdSteelDoor` 的开门代码（铰链贴面／开角 92°→85°／
双开门转 180° 的扇侧），用户实测直接判"开门完全错误、半透明材质被替换、面目全非"，要求整轮回退（已 `git checkout HEAD --` 恢复）。

**正确顺序**：改网格 → 出离线渲染核对 → 进游戏只验"能放、能开" → 确认无回归后再谈代码。
原构件代码一律按**包围盒**摆位，等比／逐轴缩放后照常工作，**一行都不用改**。
缩放包里的模型必须**保留材质槽**（默认只留一个空槽，包门扇 `[M_Door, M_Glass]` 的半透明小窗会丢），
做法见 [资产模型工作流](../../asset-model-workflow/SKILL.md) 的"缩放已有网格"一节。

### 照着做成功的那一轮（2026-09-18 第二轮：门框进深 40 cm + 双开门门扇换单开门模型）

同样的需求又做了一次，这次只改网格、C++ 只换路径，一次过。可复用的结论：

1. **逐轴缩放要挑轴**：门扇的 X（进深）是"名义板厚"的来源，**不要跟着一起缩**——板厚必须保持
   `2×LeafHalfThicknessCm`（这里 5 cm），铰链深度与摆向才对得上；只缩 Y／Z 到洞口格。
   门框这类装饰件才适合三轴全缩或只缩进深（单扇门就是 24.84 → 40 只缩 X，占格仍 (2,6,11)）。
2. **包围盒原点要归零**：`AlignGeometry` 给"转 180° 的那一扇"用的是
   `相对 Y = ∓LeafHalfY − Origin.Y`，只有"原点＝包围盒中心"时才把扇摆到洞口里。
   包的模型原点常在角落（`SM_Door` 偏 (0,−45,+100)），缩放后要**平移把包围盒中心放回网格原点**，
   否则转过 180° 的那一扇整体偏半个门宽。
3. **烘焙容器用 `duplicate_asset`**：本版 Python 没有 `unreal.StaticMeshFactoryNew`，
   复制一份源资产当容器再 `copy_mesh_to_static_mesh` 覆盖几何，材质槽会一并带过来；
   无论如何都要读回 `static_materials` 槽数（门扇应是 2，含 `M_Glass`）。
4. **环状网格（门框）用三角面碰撞**：清空简单碰撞 + `CTF_USE_COMPLEX_AS_SIMPLE`，包成盒会堵死门洞；
   门扇这种实体薄板可以留 `AlignedBoxes`。
5. **同名常量别放匿名命名空间**：同一个模块里多个 .cpp 都写 `const TCHAR* DefaultLeafMesh=...`，
   UBT 的 unity 合并把其中两个并进一块就报 `C2374 重定义`；常量名按类区分
   （`WindowLeafMesh`／`SingleDoorFrameMesh`／`DoubleDoorLeafMesh`）。

### 同一天第三轮：把高度也统一成 2.2 m（门、门框同步）

6. **"同步"要认准哪个尺寸是基准**：用户要"门、门框都同步调整"时，**外廓取整格、洞口与门板按同一比例走**。
   包门框的洞口实测正好＝门板尺寸（`SM_DoorFrame` 洞口 90 × 200 ＝ `SM_Door` 的 90 × 200），
   所以门框与门板套**同一个 Z 比例**（220/212）后洞口仍严丝合缝；自有框（双开门）则直接把门扇取
   "洞口 − 1 cm 缝"。结果：单扇门框 40 × 114 × 220（占格 (2,6,11)，门板 207.55）、
   双开门框 40 × 200 × 220（占格 (2,10,11)，洞口 184×204，门扇 91.5×203）。
7. **保存必须核实真落盘**：烘焙脚本里的"读回"是**同进程内存值**。并行会话的 Unreal 进程占着包时，
   保存会静默失败（`LogFileManager: Error moving … (Error Code 32)`、`LogSavePackage: Error: Error saving …`），
   表现是"脚本 PASS、磁盘 `.uasset` 却没变"。要等那些进程退出后重跑，并核对文件 mtime 变新；
   判断有没有别的会话在跑：`Get-CimInstance Win32_Process -Filter "Name='UnrealEditor.exe' OR Name='UnrealEditor-Cmd.exe'"`。
8. **把"可调数值"收敛成一处**：用户在同一天把高度从 2.2 m 又改成 2.4 m（第三→第四轮）。为了不再改一圈文件：
   - **资产名不带可调尺寸**（`SM_SingleDoorFrame_D40`／`SM_SingleDoorLeaf_D40` 只标进深），C++ 只认路径，改高度不用动；
   - 只保留一个高度常量（单扇门脚本的 `HEIGHT_CM`；双开门脚本的 `FRAME_H`，门扇高 = `FRAME_H − 2×边梃 − 1 cm` 推出来）；
   - **调色板占格按包围盒逐轴 /20 向上取整算**（`register_*_prefabs_*.py` 里从 `mesh.get_bounds()` 算），不再写死 `CELLS`；
   - 单扇门的三条调色板条目（`door_wood/stone/marble`）除了占格，还要把 `Mesh` 指向当前门板，
     否则抽屉缩略图与预览 ghost 会停在旧门板尺寸；被取代的旧门板资产移入 `trash/<task>/` 并记散列。
