# 多进程 UE 检查：运行负载与构建证据

在用户明确要求真实主客机、渲染或尸体检查时使用。整理、技能更新和普通构建不自动触发这些检查。

- 固定本轮待测 DLL、原生插件、资产版本、角色/端口和隔离存档；保留每个端的日志与结果，记录自己创建的 PID，收尾只结束这些进程。
- DLL 拷贝可以隔离链接占用，但不会隔离同一机器的 RAM、VRAM、CPU 或后台资产编译。不能因为使用了独立测试目录就并发叠加多套 UE 渲染检查；沿用既有批次互斥，先考虑无渲染网络检查，再按需要逐端采集画面。
- 启动前结合正在运行的 UE/构建及实际余量安排并发。等待、资产编译或系统重启中断的测试不能算通过；大量 PSO 等待和内存余量警告也不能直接归因到待测玩法。
- M66 V23 检查期间，日志出现内存余量不足，Windows 随后记录 Kernel-Power 41/6008，BugcheckCode 为 0。它证明异常重启和该轮中断，**不能证明内存、GPU、供电或某段玩法代码就是根因**。
- 共享构建产物的时间戳不足以单独证明源码已进入 DLL。必要时可比较 MSVC 对象内 CodeView 源码校验和（按记录种类处理 MD5/SHA1/SHA256），并结合成功链接记录、对象与 DLL 的对应关系和最终文件散列。对象校验只证明对应源文本被编译，不能替代链接、头文件一致性或运行验收。
- 临时宿主若含指向正式 Content/插件资源的目录 Junction，归档遍历必须跳过 reparse point。先记录链接目标，明确只处理链接或宿主自身，不能递归移动/散列目标资产。归档保存散列和恢复边界。
- 用户叫停后停止本任务检查，保留失败/中断证据和待测项。后来请求整理、Git 推送或沉淀 SKILL，不视为恢复游戏检查的授权。

## 工作站联机场景的有效前置

- 付费批次夹具要包含正式校验要求的 Escrow、成品数据/实例 ID 和配方快照。先确认影子档案实际创建成功；错误种子被拒绝不能算作翻页 RPC 的失败。
- 查清 PersistState 对 RuntimePawn 的要求再选轻量 Pawn。FPSGAME 的影子保存需要绑定权威 FPS 角色；空地图里还要固定移动状态、避免操作者与旁观者重叠，并记录视点/距离。保持正式可达性校验，不为夹具关闭它。
- Logout 检查必须走正式退出钩子；不要在测试 GameMode 中提前 Suspend，否则会掩盖“角色先销毁、工作站未释放”的实际缺陷。
- 同机 RHI 检查可复用项目已有角色外观隔离开关，避免加载与被测对象无关的身体资源。先让第一位客机退出再连接晚加入者可限制同时进程数，但报告必须说明这不覆盖三端同时在线。
