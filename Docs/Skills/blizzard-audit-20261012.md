# 暴风雪源码排查（2026-10-12）

用户要求确认持续时间、影响范围的等级成长，并找出 bug 和遗漏。此次读取当前数据、运行源码、UI、存档／联机路径及特效作者，按 JSON 计算成长表，核对 15 个直接运行资产文件存在。未修改玩法或平衡数据，未启动 UE 图形编辑器、游戏、PIE、渲染、构建或自动回归；以下代码结论不等于实机复现。

## 成长结论

持续和范围均已接入实际玩法，并非只有说明文字。

- `ColdSteelBlizzardModel.cpp:25`：半轴 Rx=(200+8L)×1.5 cm，Ry=(124+5L)×1.5 cm。
- 同文件29行：持续=5+floor((L−1)×5/19) 秒。
- `FPSBlizzardComponent.cpp:132` 在开始凝聚时保存 `CastSnapshot`；区域构造使用这一份数据。
- `FPSBlizzardZone.cpp::DamageTick` 按快照半轴和目标身体半径筛选真实伤害目标；`Tick` 按快照持续时间结束伤害。
- `ColdSteelSkillPage.cpp:419` 当前级／下一级也读取同一 `BlizzardStats`。

持续档位：1–4级5秒，5–8级6秒，9–12级7秒，13–16级8秒，17–19级9秒，20级10秒。范围每级增加：长半轴12cm、短半轴7.5cm，即完整宽度+24cm、深度+15cm。普通目标完整停留时，每0.5秒一拍、释放立即首拍，精确结束点不增加一拍；另有0.6秒视觉消散，不延长伤害。

成长在下一次开始凝聚时取新快照；已凝聚、已释放的暴风雪不会中途改尺寸。最大施法距离基础9.75米，不随等级增长；当前法杖 `magicRangePercent` 只放大落点距离 `C.Range`，没有放大暴风雪半轴。这是当前实现口径，不能直接当作遗漏并擅自改平衡。

## 已确认的逻辑与接入缺口

### 1. P1：联机释放失败后可能留下施法占用和冻结冷却

证据：`FPSBlizzardComponent.cpp:159–161` 在服务器回执前先清本地预留、付款和 bCommitted；同文件210行拒绝处理先清 bNetPaid 再 CancelPending。`ColdSteelPlayerState.cpp:994` 的释放失败只 Reject，不退影子档付款、不清 PendingCastSkill。1034行会继续拒绝新的施法；126行看门狗只覆盖火球。`ColdSteelProfileRuntime.cpp:924` 又会冻结仍处于 bBlizzardReserved 的冷却。

触发场景：客人释放时走到施法距离边界之外，服务端距离结果与客户端不同，或服务端区域初始化失败。预期应保留可重试的云或一致退款清占用；当前本地云已消失，服务端仍保留未释放事务，后续其他魔法也可能持续被拒绝。风险由代码分支确认，未在联机中执行复现。

建议先修失败回滚事务，并让成功回执后再最终清除本地付款状态；超时和取消需使用同一事务状态，不能只补 UI 提示。

### 2. P2：联机服务端落点检查没有与单机对齐

证据：`FPSBlizzardComponent.cpp:195` 的 NetCommitZone 只核对水平距离和上报法线 Z，直接在上报点创建区域；没有重新确认落点地面、施法者到落点的遮挡。单机释放路径152–155行有视线和距离检查。服务端 Phase1 的暴风雪分支也没有这两项补充检查。

触发场景：松键后地面／门／障碍发生变化，或客户端上报不再成立的落点。预期服务端重验实际地面及通路；当前仍可能在遮挡后的地面或悬空点生成暴风雪。区域生成后的目标遮挡仍存在，这不代表区域内所有伤害都可以穿墙。

### 3. P2：联机区域的结束表现和时间没有完整同步

证据：`FPSBlizzardZone.cpp:236–243` 客户端 Age 从自己的初始化后累计，没有服务器起始时间；也没有在 Duration 到达时设置 bFinished。服务器252行调用 Finish 才会设置结束状态。181–186行停止雨雪／寒雾及坠冰出生依赖 bFinished。

结果：客户端可在伤害已经结束后继续出生装饰落冰；高延迟或区域迟进入相关性时，云的起始／淡出与权威伤害时钟不一致，最终可能由服务器销毁而突然消失。应同步起始时间与结束阶段，只在服务端结算训练。

### 4. P2：联机客人的四区域上限漏在权威入口之外

证据：`FPSBlizzardComponent.cpp:80` 只在 Allowed 检查本组件 Zones 数量；客人释放分支161行不会把服务端复制区域添加到这个数组。NetCommitZone 在195–208行无上限检查，成功后直接 Zones.Add。

触发条件：无冷却模式或极短冷却允许区域重叠时，客人可突破文档约定的每玩家四个区域上限。普通基础冷却下不容易碰到。应在服务端创建区域前按活跃 Zones 再判上限。

### 5. P2：技能详情仍展示旧操作、旧冷却和旧菜单行为

证据：`ColdSteelSkillPage.cpp:817` 行标签仍为「起手冷却」，819行仍写“瞄准地面按键施放”“有效起手锁定区域并开始冷却”“打开菜单退款”。现有组件已经是先凝聚、再选点释放；Profile 在预留期间冻结冷却；完成凝聚后打开菜单只收起预览、保留云。

影响：用户按说明操作时会误以为第一次按键没有施法、冷却没有开始或菜单没有退款。JSON 的简短描述已更新，但详情页硬编码正文遗漏。应统一到现行两阶段施法合同。

### 6. P2：暴风雪升级通知遗漏

证据：`ColdSteelSkillModel.cpp:385` 的 NoticeDefinitions 没有 BlizzardSkill，函数后续也没有独立暴风雪通知路径。伤害奖励仍在 `ColdSteelBlizzardModel.cpp::FinishBlizzardCast` 正常调用 AddExperience。

结果：达到升级门槛后技能可实际升级，但不会经过统一通知队列产生对应的升级提示。应加入定义和暴风雪的范围／时长摘要。

### 7. P2：F6 技能调级入口遗漏

证据：`Development/ColdSteelDevelopmentTools.cpp:53–57` 的 SkillCatalog 无 blizzard，61–74行的 DevelopmentSkillDefinition 也没有对应分支；93、106行拒绝目录外技能。面板直接用该目录构造技能下拉。

结果：无法通过现有 F6 技能列表选择暴风雪进行升一级／升满级。应补当前目录和定义路由，不新增第二套调级入口。

## 表现风险／尚未完善的部分

### 屋顶适配只处理区域中心，未覆盖整个云层

`FPSBlizzardZone.cpp:64–66` 创建时只从区域中心向上探测一次，整片区域共用高度。`build_blizzard_charged_v3.py:146` 的云团横向散布到完整区域，宽度随技能半轴增加，仍有旋转和相机朝向。

当区域跨越横梁、斜顶或不同高度的天花板时，中心未命中低顶不能保证周边云团不进入天花板。它已具备基础室内适配，但没有雷暴领域本轮加入的多点净空／云片竖直限制。实际遮挡程度需要用户场景画面确认；不把未运行的画面结果写成已复现。伤害从地面区域独立结算，不受乌云是否可见直接控制。

### 客户端区域初始化仍同步加载资源

`FPSBlizzardZone.cpp:262` 在 Tick 调用的 NetInit 中执行15次 LoadObject。玩家组件已有异步预热，缓存就绪时未必有明显问题；但远端区域先到或资源冷缓存时仍存在同步加载停顿风险。本轮没有做帧时间采样，不宣称已发生卡顿。

## 已有实现与非缺陷边界

- 当前15个直接引用 `.uasset` 均存在，Blizzard／IceSpike／IceWall 已列入 Cook 目录；只确认文件与配置，没有做包加载、Cook或材质运行验收。
- 伤害、寒冷叠层、整场修炼、存档迁移、未释放读档退款、快捷栏绑定／拖拽及当前／下一级数值已有路径。
- 已保存的区域云生命周期曾修正过；现行作者将系统和核心粒子时长接到 StormDuration，本轮不能再把旧“五秒固定云”当作当前已确认 bug。
- 暴风雪仍配置 `requiresStaff=false` 且介绍明确无需法杖。上一轮用户只要求雷暴领域改成法杖限定，未把该要求自动扩展到暴风雪。
- 坠冰是装饰，伤害按每0.5秒的区域拍统一结算；这属于原有技能设计，并非漏写冰锥命中伤害。
