## 0. 结论

炼药分支已经从“点按钮发药”做到了完整的单机闭环：进入页选配方/备料，台面投料/研磨/调火/搅拌/沙漏/装瓶，手册提供配方知识，服务端权威结算，支持暂存、继续、领取、作废退半和联机复制。手册的实体书、目录、书签、拖页和纸页排版完成度尤其高，89 项流程检查和 10 阶段真实 socket 检查已有记录。

但以“可玩、可读、可学会、不会误操作”的标准看，当前更偏“功能完成”，还存在一批体验与安全边界的缺口。**未发现 P0 级崩溃、丢档或阻断性逻辑错误；建议在下一轮用户测试前先处理 6 项 P1**：

1. 阅读手册或窗口失焦时，火候继续推进，但玩家看不到温度/火力，可能无声烧焦。
2. 装瓶是一次点击即提交；未完成时误点会直接失败并消耗材料，正常操作里没有二次确认或显式取消。
3. 投料顺序、研磨不足、搅拌方向、过热等失误在过程中没有可见反馈，只能结算时才知道。
4. 搅拌按“角速度绝对值×时间”累计，来回抖动也能凑满“两圈”，不符合手册描述。
5. 实景模式仍显示战斗 HUD；底部提示条与快捷栏在屏幕底部重叠，且提示条不拦截点击。
6. 进入页操作说明不完整；右键研磨、滚轮调火、沙漏和装瓶入口只能靠逐件悬停发现。

另有若干 P2/P3：失败批次的下一步（I-04）、字号档位与滚动条（U-02/U-03）、状态语义色（U-04）、同步导入图标（P-01）、逐帧可达性检测（P-02）、键盘焦点/下拉（U-10），以及最多 3 个材料槽与数据允许 6 个输入的数据边界（I-08）值得排期。

## 3. UI 审计

### U-01【P1】实景底部提示条与快捷栏重叠，且提示条不拦截点击

`ColdSteelAlchemyWidget::Layout` 把底部提示条放在 `Size.Y - 68`、高 52px（`ColdSteelAlchemyWidget.cpp:230-231`）。快捷栏在 `ColdSteelHotbarLayout.cpp:78-79` 是贴底 `-12`、高 `48 + 2×8 = 64px`，即屏幕底部 `12–76px`。两者在底部 `16–68px` 区间几乎完全重叠。

实景模式只调用 `HUD->SetAlchemyManagement(false)` 关闭背包，并不会隐藏快捷栏、体力条、右侧导航、右下武器栏（`ColdSteelAlchemyWidget.cpp:243`、`ColdSteelAlchemyController.cpp:45-50`）。炼药控件 ZOrder 60，提示条玻璃底不透明度约 97%，所以快捷栏 64px 高度中有 52px 会被盖住，只露出顶部与底部各几像素；如果快捷栏在更上层，则会顶穿提示条。

同一处 `SetWorkVisibility` 把 `Controls`、`IngredientPanel`、`FinishPanel` 全设为 `HitTestInvisible`（`ColdSteelAlchemyWidget.cpp:236-237`）。V6 明确要求“状态小窗不拦截台面点击”，两侧面板这样做是有意的；但底部提示条是安全提示，不是操作窗，建议单独处理：至少让它拦截点击，避免点在提示文字上却命中身后的台面物件。

**建议**

- 给 HUD 增加“工作台视图”开关：实景炼药时隐藏快捷栏、体力条、右侧导航入口、武器栏和准星；保留生命/魔法（或全部收起），退出恢复。这样既解决重叠，也更沉浸。
- 若不想改 HUD：把提示条移到快捷栏上方（`Size.Y - 76 - 52`），并把 `FinishPanel` 设为可命中；两侧状态窗保持 click-through。
- 实机至少检查 1280×720、1920×1080、2560×1440、3440×1440 四种宽度。

### U-02【P2】实景面板字号不在六档内，关键温度不是数字字体

实景面板的创建代码（`ColdSteelAlchemyWidget.cpp:91-107`）：

| 文本 | 当前字号/字体 | 建议 |
| --- | --- | --- |
| “备料余量”“坩埚” | 15 / Noto Sans | 16 Medium（分区标题） |
| 材料名 | 13 / Noto Sans | 14（正文） |
| 研钵选料状态 | 12 / Noto Sans | 12（辅助，保留） |
| 温度 + 火力 `LiveStatus` | 18 / Noto Sans | 24 JetBrains Mono 温度 + 14 Sans 火力，或整体 16 |
| `Instruction` 长说明 | 13 / Noto Sans | 14（正文） |
| 底部提示 | 13 / Noto Sans | 14 或 12 |
| 悬停标题 | 15 / Noto Sans | 16 |
| 悬停正文 | 13 / Noto Sans | 14（长说明可 14 换行） |

正式规则把 15/18/13 排除在六档之外（`ui-cold-steel-design-system.md` §4）。更实质的问题是：**温度是本小游戏最核心的实时数值，却和“低火”一起用 18px 无衬线字体**，没有像 HUD 弹药/体力那样用 24px JetBrains Mono。建议拆成两个 TextBlock：`62.4` 用 24px Mono，`°C · 低火` 用 14px Sans，便于扫读。

另外 `LiveStatus` 用 `%.0f`（`ColdSteelAlchemyWidget.cpp:215`），温度计和进入页用 `%.1f`（`PotionWorkbenchVisualComponent.cpp:177`、`ColdSteelAlchemyEntryData.cpp:86`），同一个温度会出现 `62` 和 `62.4` 两种读数。建议统一到 0.1°C，或至少同一屏内一致。

### U-03【P2】实景两侧滚动条未套 6px 冷钢样式

`Build` 的两侧面板 `Panel` lambda 只创建了裸 `UScrollBox`（`ColdSteelAlchemyWidget.cpp:86-87`），没有 `SetScrollbarThickness`。项目多数面板设置 6px（锻造、木工、枪匠、图鉴、仓库等；状态效果 HUD 另有 4px 例外），正式规则 §3 也要求中性灰约 6px。进入页已经正确设置（`ColdSteelAlchemyEntryStyle.cpp:48`），实景两侧漏了。

**建议**：在 `Panel` 中加 `Scroller->SetScrollbarThickness(FVector2D(6/Scale)); Scroller->SetScrollbarPadding(FMargin(4/Scale,0,0,0));`，并在 `Layout` 的 DPI 变化处同步更新。

### U-04【P2】页脚状态与工艺警告缺少语义色

`Status` 创建时固定 `TextSecondary`（`ColdSteelAlchemyWidget.cpp:125`），`Refresh` 只改文本（`:198-209`）。因此：

- “材料不足”“本炉或背包正在同步”“保存尚未确认”与普通说明同色；
- `Instruction` 里的“药液泛褐，出现焦味”仍是正文色；
- `LocalNotice` 的失败提示也是灰色。

材料行有红色“缺 N”，但最关键的一行状态没有颜色层级。建议按状态设置：正常/暂存 `TextSecondary`；保存/同步 `TextTertiary` 或 `Warning`；缺料/失败/焦化 `Danger`；准备就绪可用 `Success` 或保持中性，避免整屏泛绿。`Instruction` 在 `Observation()` 含“焦”或温度超过配方上限时用 `Danger`/`Warning`。

### U-05【P1】进入页操作说明不完整，右键研磨/滚轮调火/沙漏/装瓶没写

进入页“操作说明”只有两段（`ColdSteelAlchemyEntry.cpp:117-121`）：

> 进入台面后直接点击材料与器具。按住搅拌棒绕锅心拖动，火候旋钮左键升档、右键降档。  
> 翻阅配方手册决定用料、火候与搅拌，观察药液和温度计判断时机。点击量瓶舀取并装瓶。

它没有说明：

- 材料**右键**选入研钵，研钵**按住左键**研磨；
- 火候还可以用**滚轮**，键盘 `1–4` 是关/低/中/高；
- 沙漏左键翻转，十秒仅辅助估时；
- 量瓶/汤勺点击即开始 4.6 秒装瓶；
- `B` 手册、`Esc` 收火暂存、再次 `Esc` 关闭。

目前这些只能靠逐件悬停发现。第一次炼药的玩家很可能不知道“右键选料—按住研磨”，也不知道沙漏能点。建议在进入页增加一张紧凑的“操作”卡（12px/14px，两列，不写下一步工序，只写控件映射），或首次进入台面时显示一次半透明操作提示。它不违反 V5 的“不显示下一步/工艺分”，因为只讲输入。

### U-06【P1】阅读手册时没有温度/火力提示，火候仍在推进

`Book(true)` 会 `Stop()`、隐藏管理页和全部操作浮层（`ColdSteelAlchemyWidget.cpp:246-257`），阅读层只有书页（`ColdSteelAlchemyBookWidget.cpp`），没有温度、火力或剩余时间。与此同时 `UColdSteelAlchemySystem::Tick` 仍按 `Advance` 推进温度和有效熬煮（`AlchemySystem.cpp:579-592`）。

原方案明确写过：

> 准备时阅读不限时；已经开启的火候在翻书时继续推进，阅读层保留小型热度提示。  
> ——`Docs/UI/potion-workbench-magic-brewing-plan-20261015.md` §4

当前实现没有这个“小型热度提示”。玩家在高火下翻到高级配方对照温区，几秒后可能已经超过上限甚至开始焦化，而画面完全看不到。这是本轮审计里最值得优先修的设计缺口之一。

**建议**：在阅读层角落加一个纯文字/细线的小读数（不套玻璃板，遵守手册例外）：`62.4 °C · 中火`，使用 14px Sans + Mono 数字；无批次或未开火时显示 `已收火`。打开手册时若正在高火，先在底部提示“火候仍在继续”。不要把它做成可点击按钮，也不要显示下一步。

### U-07【P3】手册加载文字没有按 DPI 换算

`ColdSteelAlchemyBookPreview.cpp:49` 使用 `GunsmithUI::TextFont(24)`，没有除以 `PixelScale`。其他面板的 `Text()` 都走 `Pixels/Scale`。在 4K/高 DPI 下，这行“正在打开配方手册…”会明显偏小。改为 `GunsmithUI::TextFont(24 / ColdSteelUI::PixelScale(this))` 或在布局刷新时更新。

### U-08【P3】悬停浮窗的限位高度是固定 126px

`UpdateHover` 用固定 `BoxSize(380/Scale,126/Scale)` 做屏幕限位（`ColdSteelAlchemyTabletop.cpp:123-127`），但正文允许 3 行以上，实际高度可能超过 126。窗口靠下时可能出现浮窗底部越界。建议在设置文本后取 `HoverPopup->GetDesiredSize()`（或按行数估算）再限位，或把正文限制在两行并给“查看手册”提示。

### U-09【P3】温度计自适应宽度取错了轴：用高度当宽度

`UpdateThermometer` 在文本变化后计算：

```cpp
const float Width = TemperatureReadout->GetTextLocalSize().Y;
if (Width > 8.4f) TemperatureReadout->SetXScale(8.4f / Width);
```

（`PotionWorkbenchVisualComponent.cpp:179-180`）

`GetTextLocalSize()` 返回的是 `(宽, 高, 深)`，这里取 `.Y` 是**字高**而不是**字宽**。字高约等于 `DigitSize`（4.3cm），永远小于 8.4cm，所以缩放分支实际不会触发；像 `65.0` 这样的四字符读数可能超出实体温度计的 8.4cm 屏幕宽度。应改为 `.X`，或在布局脚本里给出可用的净宽并在运行时使用同一常量。

### U-10【P3】所有键盘事件都被无条件吞掉，下拉/页签的键盘操作可能失效

`NativeOnKeyDown` 只对 Escape/Tab/B/方向键（书内）/1–4/F/R/T/A/D 分支处理，最后却无条件 `return FReply::Handled()`（`ColdSteelAlchemyWidget.cpp:365-377`）；`NativeOnKeyUp` 同样（`:378-379`）。这意味着：

- 进入页的配方 `UComboBoxString` 弹出后，如果按键事件冒泡到父控件，方向键/Enter/PageDown 会被父控件吃掉，无法用键盘选配方；
- 页脚按钮的键盘激活、滚动区的键盘翻页也没有可靠的焦点路径；
- 共享 UI SKILL 的“键盘/弹出层焦点返回”与“输入被 UI 意外吞掉”检查项在这里没有满足。

**建议**：只对明确使用的键返回 `Handled`；其余键 `return Super::NativeOnKeyDown(...)`。由于面板是 `FInputModeUIOnly`，未处理的键不会穿透成世界攻击；如果担心某个键穿透，可在控制器层显式屏蔽移动/攻击键，而不是让面板吞掉全部键。关闭/打开弹出层时保存并恢复焦点到原控件。

## 4. 游戏实现与交互审计

### I-01【P1】搅拌按“角速度绝对值×时间”累计，抖动也能凑圈数

服务端 `Advance` 的搅拌进度是：

```cpp
Working.Progress[Current] += Dt * .75f * FMath::Abs(StirDirection);
```

（`AlchemySystem.cpp:453-460`）

方向判定只看当前 `StirDirection` 的符号（`direction=0` 时任何方向都算，`direction=1` 时只算顺时针）。UI 每 0.1 秒把鼠标角速度发成 `Speed`（`ColdSteelAlchemyWidget.cpp:353-359`），`ProcessInput` 只保存瞬时值。结果是：

- 基本配方（方向不限）可以左右来回快速抖动，速度绝对值一直很大，2 圈很快完成；
- 有方向的配方可以小幅顺时针抖动（每段都满足正号）累积进度，不需要真正绕锅心转满两圈；
- 手册写的是“搅匀两圈”，视觉上的 `StirPhase` 也在转，但判定并没有验证“连续转满”。

这既是可以被利用的捷径，也让“搅拌”手感偏“摇鼠标”而不是“画圈”。

**建议**：把“瞬时速度”改成“有符号角度增量”。UI 已有 `DragRadians`，可以每 0.1 秒把角度增量（或累计角度）随 `EAlchemyOp::Stir` 一起发给服务端；服务端：

1. 过滤单帧超过 π/2 的跳变（已有 UI 侧过滤，服务端仍需复核）；
2. 只在方向匹配时累加有符号角度；
3. 每累计 ±2π 记 1 圈，`Progress` 用圈数而不是时间；
4. 方向反转时清零连续段或记一次方向错误，避免“抖回去再抖回来”。

如果不想改协议，至少要求 `StirDirection` 连续同号超过一个短窗口才计入，并禁止反向段累积；但这仍是“时间”不是“圈数”，不如角度可靠。

### I-02【P1】失误在过程中完全不可见，只能结算时知道

`Fault()` 只做两件事：增加 `Working.Penalty`、把文本塞进 `Working.Faults`（`AlchemySystem.cpp:330-334`）。`Publish()` 的台面状态没有失误字段（`:593-607`），`Observation()` 只根据焦化秒数、融合度、温度给出“药色/沸腾/焦味”（`:135-150`）。因此：

- 投料顺序错了：没有提示；
- 结晶没磨够就投：没有提示（只加 15 分惩罚）；
- 搅拌方向错了：只有惩罚，没有声音/文字/液体变化；
- 投料时温度不对：没有提示；
- 过热：只有超过 90°C 后 `ScorchSeconds>3` 才出现“焦味”，且没有颜色/声音强调。

V5 的“现场不显示下一步、步骤进度或即时工艺分”是对的，但**“刚刚做错了什么”不是下一步提示，也不是分数**。现在玩家无法在过程中纠正，失败后只能看到一列文字，学习成本很高。

**建议**：

- 在右侧 `Instruction` 下方增加一行“工艺”短讯，只在失误发生时出现 2–3 秒，例如“投料顺序偏离手册”“结晶仍偏粗”“搅拌方向不对”“药液开始焦化”；不显示分数、不显示正确步骤。
- 同步一个短音效/液体颜色/蒸汽变化；焦化用 `Danger` 色 + 焦味音。
- 服务端在 `FAlchemyBenchState` 增加 `FaultSerial/LastFault`（或复用 `Notice` 的独立字段），`Publish` 时带上；客户端只在变化时刷新，避免 10Hz 字符串重建。
- 失败结算仍保留现有 `Faults` 列表和“工艺偏差”详情。

### I-03【P1】装瓶一次点击即不可撤销，未完成时误点直接失败

`CanTableAct(50)` 的条件是“锅里有料 + 温度不高于装瓶上限 + （自由炼制或工序已完成）”（`ColdSteelAlchemyTabletop.cpp:27-29`）。自由炼制下，开炉后基液已入锅，温度 20°C 也满足条件；玩家点一下量瓶/汤勺就会进入 4.6 秒装瓶（`AlchemySystem.cpp:481-497`），随后 `Finish()` 发现工序没完成，直接 `Fault(...,100)`、`bPassed=false`、本炉失败，材料只退一半。

悬停虽然写了“过早装瓶会失败”，但：

- 点击就是提交，没有二次确认；
- 4.6 秒动画期间没有明确的取消按钮（`ProcessInput` 在 `bBottling` 时直接返回）；只有 Esc 收火暂存会经 `Suspend` 清掉 `bBottling` 并中断装瓶，但玩家通常不知道这个时序窗口，且窗口一过就无法挽回；
- 失败后主动作是禁用的“本炉失败”，还要再找“作废退料”。

对于“看手册判断时机”的核心玩法，误触代价过高。

**建议**（按侵入性从小到大）：

1. **未完成时要求按住 0.4–0.6 秒**才装瓶；完成时仍可单击。悬停明确写“尚未完成，按住确认会失败”。
2. 或未完成时第一次点击只弹出“本炉尚未完成，装瓶将失败”的确认，第二次才执行；完成时不确认。
3. 在装瓶动画前 1 秒留一个“收手”窗口：`Bottle` 只锁定动作，真正 `Finish` 前允许 `EAlchemyOp::Stop` 取消并保留批次；这需要服务端和网络状态一起改，成本较高。
4. 失败后的主动作改成“作废并退回一半”（见 I-04），至少让误触后的恢复路径清楚。

### I-04【P2】失败批次的主动作是禁用按钮，下一步不明确

`Refresh` 在失败时把主按钮设为 `Caption("本炉失败")` 且 `SetIsEnabled(Can=false)`（`ColdSteelAlchemyWidget.cpp:207-210`），可用的只有“作废退料”。页脚状态会写“本炉失败 · 可作废退回一半材料”，但视觉上玩家面对的是一个灰掉的按钮和一个不明显的次按钮。

**建议**：

- 失败时在页脚上方加一行明确的下一步：“本炉失败：点击『作废退回一半』结束本炉；不领取成品。”
- 或把失败时的主动作改为“作废并退回一半”，复用现有两步确认（`Action 12` 的确认逻辑），不要把 `Action 10` 的“开炉/领取”语义混进去。
- 给“作废退回一半”在失败态加 `Danger` 细边/文字，仍保持等宽按钮规范。

### I-05【P1】窗口失焦后火候继续，可能无声烧焦

`NativeTick` 在 `FSlateApplication` 不活跃时只调用 `Stop()`（`ColdSteelAlchemyWidget.cpp:326`），`Stop` 发送的是“放下器具”，不是“收火”。`UColdSteelAlchemySystem::Advance` 仍按 `HeatLevel` 升降温（`AlchemySystem.cpp:417-467`）。

单人模式如果游戏因失焦暂停，问题会被掩盖；联机/未暂停时，玩家 Alt-Tab 出去看攻略，回来可能已经焦化。和 U-06 一样，这是“玩家看不见的时候系统还在惩罚”。

**建议**：

- 失焦超过 1–2 秒：自动把火候降到 0，并显示“窗口失焦，已收火；本炉保留”；
- 或失焦即 `Suspend()`（保存并关闭实景），回来从管理页继续；
- 至少不要保持高火继续推进。若担心误判（例如短暂切输入法），可以只降火不暂停。

### I-06【P2】“可搅拌”金边与实际是否计入不一致

`CanTableAct(31/32)` 只要求“锅里有料”（`ColdSteelAlchemyTabletop.cpp:26`），但 `Advance` 只在**当前步骤**是 `stir` 时累计进度（`AlchemySystem.cpp:453`）。所以：

- 当前步骤是投料/研磨/加热时，搅拌棒仍显示金边、手型光标，玩家按住拖动，勺子会转，但完全不计进度；
- 对自由炼制，如果玩家在错误的步骤搅了很久，什么也不会发生，也没有提示。

同样的问题在“搅拌完成后的继续搅拌”：`Refresh` 只对非自由炼制在步骤变化时自动 `Stop()`（`ColdSteelAlchemyWidget.cpp:212`），自由炼制下会一直保持搅拌动作。

**建议**：要么把 `CanTableAct(31/32)` 收紧为“当前步骤是 stir 或存在未完成的 stir 步骤”，并在不可计时给“现在搅动不计入工序”的提示；要么让搅拌像研磨一样可以提前累计到未来的 stir 步骤（更符合自由炼制），但需要同步调整顺序评分。两者选一，不要让金边承诺一个不会发生的进度。

### I-07【P3】旧批次重新翻沙漏会把当前熬煮进度清零

非自由炼制的 `Timer` 分支在 `bTimerRunning` 时执行 `Working.Progress[Current]=0`（`AlchemySystem.cpp:362-368`）。手册和文档写的是“计时中重翻会重计当前时段”，但当前实现把已经累计的整段熬煮进度也清掉了。新配方全是 `freeBrewing=true`，所以只影响旧批次；仍建议改成“只重置本次沙漏段，不重置已累计有效时间”，或在提示中明确“重翻会重置本段”。

### I-08【P2】数据允许 6 个输入，但台面只有 3 个材料槽

- `DecodeRecipe` 允许 `Inputs.Num()<=6`（`AlchemySystem.cpp:64`）。
- 台面模型/命中只有 3 个槽：`PotionWorkbenchVisualComponent.cpp:98-102` 创建 3 个 `IngredientParts`，`AlchemyTabletop.h:14` 只有 3 个位置；`CanTableAct` 也只接受 `Id 100–102`（`ColdSteelAlchemyTabletop.cpp:20-24`）。
- 进入页的材料表可以显示 6 行，手册也能写 6 个材料，但第 4–6 个在台面上**没有模型、没有命中、无法投料**（只能靠不存在的按钮，实际没有）。

当前 8 份配方最多 3 个输入，所以还没有触发。但这是数据合同与实现能力的硬冲突，后续加配方很容易踩。

**建议**：短期内把 `DecodeRecipe` 收紧为 `Inputs.Num()<=3` 并在加载时明确报错/日志；或者扩展 3 个槽位、命中、模型、布局和 `CanTableAct`。不要保留“数据可以 6、台面只能 3”的沉默状态。

### I-09【P3】重复材料 ID 未校验，`Poured` 聚合会算错

`DecodeRecipe` 只校验每个输入的数量范围，没有拒绝同一 `item` 出现两次（`AlchemySystem.cpp:46-52`）。而 `Poured`/`Reserved` 是按 `Item` 聚合的 `TMap`：

- 两个输入都是 `alchemy_redvein_extract`、各 1 份时，投 1 份后 `Poured=1`，两个槽的 `CanTableAct` 都会认为“已满”，第二个槽永远投不进去；
- 退款和进度也会按合并数量计算，和 UI 的两个材料行不一致。

当前数据没有重复项，属于潜在数据合同问题。建议在 `DecodeRecipe` 用 `TSet<FString>` 拒绝重复，或把输入改成按槽位计数。

### I-10【P3】研磨会把同种材料全部标记为“已开封”

`ProcessInput(Grind)` 第一次研磨就 `OpenUnits(Id, Reserved(Id))`（`AlchemySystem.cpp:407-413`），把该材料**所有**已备料单位都记为已开封。未完成时作废只退未开封材料（`DiscardRefund`，`:513-531`），所以：

- 备了 2 份结晶，只磨了 1 份就废弃，2 份都不退；
- 备了 2 份，只投了 1 份、没研磨，废弃会退 1 份。

如果设计意图是“把整批材料倒入研钵即全部开封”，这没问题；如果意图是“按实际处理量”，则应按研磨完成/投料单位逐份标记。建议在文档里明确一句，避免玩家觉得退款不一致。

## 5. 性能、存档与联机

### P-01【P2】进入页构造时同步导入 8 张配方图标

`NativeOnInitialized` 对每个配方执行 `FImageUtils::ImportFileAsTexture2D(...)`（`ColdSteelAlchemyWidget.cpp:65-69`），在游戏线程同步读盘/解码 PNG；`Images` 是控件成员，每次重新打开工作台都会重新导入，没有跨面板缓存。项目已有物品图标/武器图标的异步缓存（`ColdSteelItemTooltip`、`ColdSteelWeaponIcons`），这里没有复用。

**建议**：改为共享纹理缓存（静态 `TMap<FString, TWeakObjectPtr<UTexture2D>>` 或现有图标服务），首次异步加载、完成后只刷新 `EntryPreview` 图片；失败保留目录占位。至少把 8 张图从“每次 NativeOnInitialized”移到一次性的缓存。

### P-02【P2】`Reachable()` 每帧做一次视线检测

`NativeTick` 每帧调用 `System->Reachable()`（`ColdSteelAlchemyWidget.cpp:328`），内部做 350cm 距离、世界/工作台归属、死亡组件查找和一次 `LineTraceSingleByChannel`（`AlchemySystem.cpp:160-170`）。服务端 `Tick` 在活动时也调用。UI 在管理页、阅读时同样每帧调用，实际只需要 5–10Hz。

**建议**：缓存 `bReachable`，在 `Refresh` 的 0.1 秒节拍或单独 0.2 秒计时器中更新；台面可见性/操作可用性仍用同一结果。服务端可在 `Tick` 内按 0.1 秒节流，不要每个积分步都查。

### P-03【P3】悬停命中随每个鼠标事件重算

`NativeOnMouseMove` 每个鼠标事件都 `UpdateHover()`（`ColdSteelAlchemyTabletop.cpp:159-173`），内部做全台面 ray-box、`FString::Printf` 和浮窗排版；高轮询鼠标（500–1000Hz）下会产生大量短命字符串和重复设置。建议按 30–60Hz 节流，或仅在指针移动超过 1–2px 时更新；悬停目标未变时只更新位置，不重建文本。共享 UI SKILL 的 “Do not rely on per-frame polling if event-driven updates are available” 与 “Debounce high-frequency hover updates” 正好对应本条和 P-02。

### P-04【P3】阅读时台面公共手册仍保留自己的两张大 RT

`UAlchemyManualComponent` 打开时分配两张 2048×1536 页纹理（`AlchemyManualComponent.cpp:105`），私人阅读器又创建一套 1400×1100 颜色/覆盖率 RT（`ColdSteelAlchemyBookPreview.cpp:90-91`）和自己的 `UAlchemyManualComponent`。阅读层是全屏的，台面手册在背后不可见，但仍保持打开和纹理。

**建议**（可选）：打开私人阅读器时通知 `UPotionWorkbenchVisualComponent` 暂时 `SetOpen(false)`/释放台面页纹理，关闭时恢复；观察者的公共手册仍按服务器页显示。注意不要改变公共页码状态。

### P-05【P2】关闭/返回请求失败时，`NativeTick` 可能每帧重试

`NativeTick` 在 `bReturn`/`bClose` 且非 `Pending` 时每帧调用 `Suspend()`（`ColdSteelAlchemyWidget.cpp:341-345`）。客户端 `Suspend()` 在无法发出请求时返回 false 且不置 `bPending`（`AlchemySystem.cpp:302-318`），于是下一帧继续尝试，形成高频 RPC/日志重试，直到网络恢复。

**建议**：给关闭/返回请求加 0.3–0.5 秒的重试间隔和“正在保存/等待网络”的提示；失败时不要每帧重发。

### P-06【P2】存档/联机路径的静态结论

现有实现已经覆盖：支付与批次原子提交、`Resume` 不重复扣料、`Claim`/`Discard` 同次清批次、背包满保留、旧回执排序、客户端只发意图、断线/拆台清理、公共手册页码校验。手册网络检查已通过 10 阶段真实 socket。**但这些不等于跨机器公网、丢包/延迟、打包专用服的验收**；当前发布记录也明确说不是干净检出即可运行的完整二进制包。

## 6. 确认过、不建议改的部分

以下看起来“奇怪”，但和现有设计/实现一致，不建议在审计里当 bug 修：

- **管理页贴在背包左侧，而不是屏幕左缘**：`screen - 2×Width` 与 HUD 背包的右贴边宽度公式一致，形成零缝双栏；在 1280/1920 下分别留 12/77px 左边距是预期结果，不是错位。
- **手册没有玻璃背景板、没有底部翻页按钮**：2026-10-16 的正式例外，实体书 + 书签 + 拖页是用户指定方向。
- **现场不显示下一步、步骤进度、即时工艺分**：V5 的核心设计，目的是让手册和观察承担判断；I-02 建议的是“已发生失误”的反馈，不应变成步骤提示。
- **两侧状态窗不拦截台面点击**：V6 明确要求，方便在面板覆盖区域仍能点到锅/器具；只有底部安全提示条建议例外。
- **旧批次必须按原手册完成工序才能装瓶**：`Bottle` 的 `!FreeBrewing && StepIndex()!=Num` 分支是有意的兼容策略。
- **领取/作废是原子事务，失败保留整批**：不要为了“部分领取”拆开。

## 8. 建议的检查与验收

当前没有炼药玩法级 commandlet，建议补一个只读合同检查（不启动地图/不写存档）：

1. 8 份配方解码：ID/版本、输入数量 ≤3、无重复材料、成品存在、`bottleHeat` 在范围、步骤动作/数量/温区/direction 合法；
2. 流程合同：每个配方至少一个可完成路径；`StepIndex` 在全部进度完成后等于步骤数；`freeBrewing` 与旧批次的装瓶分支；
3. 退款合同：未完成只退未开封；完成后按材料合并后 `floor(total/2)`；1 份退 0；背包满整批保留；
4. 快照合同：旧配方/旧步骤数的批次仍可解码、可作废、不可用新配方覆盖；
5. 网络合同：非法页码、重复请求、错误 JobId/Revision、断线清理（可复用现有手册审计夹具）。

实机测试建议覆盖：基本/中级/高级/特级各一炉；高火读书 30 秒；Alt-Tab 30 秒；未完成误点装瓶；背包满领取；失败后作废；暂存后继续；两人抢同一台；客机晚加入；1280/1920/2560/3440 四种宽度。
