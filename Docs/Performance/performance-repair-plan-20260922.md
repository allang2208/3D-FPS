# 性能面板可靠性与图标卡顿修复方案

状态：第 1 批已实现并完成 Editor 构建，见 [实现记录](performance-event-instrumentation-20260922.md)；第 2、3 批仍为方案。依据 [离线排查报告](D:/FPS3D/FPSGAME/Docs/Performance/performance-offline-diagnosis-20260922.md)。按用户要求先保证面板可靠，再优化帧数；本轮未操作 UE、未执行运行测试。

## 执行顺序与范围

| 批次 | 目标 | 交付结果 |
| --- | --- | --- |
| 1 | 补齐本次卡顿的观测盲区 | 同一份 JSON 能回答哪一帧、哪件武器、哪个阶段发生长耗时；现有图标行为保持原样 |
| 2 | 移除图标路径的重复初始化及同步阻塞 | 按需求请求图标，共享最小装配结果，异步准备与回读 |
| 3 | 定位持续约 54 ms 的 Game 帧时间 | 基于后续可用采集按实测耗时决定具体优化对象 |

第 1 批独立交付，不能将第 2 批的架构改造作为面板补录的前置条件。第 2 批针对秒级尖峰；第 3 批才负责持续帧率。当前数据不支持承诺目标 FPS 或降低场景画质。

## 批次 1：先修面板可靠性

### 1.1 保存可追溯的帧和事件

改动：`Source/FPSGAME/UI/FPSPerformanceMetrics.h/.cpp`、`FPSPerformanceMetricsExport.cpp`。

- 利用已有帧环形缓冲导出窗口内原始帧：会话 ID、完整引擎帧号、单调时间、帧时、暂停/后台状态，以及采样有效性。
- 明确导出峰值对应的帧 ID，并输出长帧列表；汇总和原始帧必须来自同一冻结快照，按会话 ID + 帧号识别重叠窗口。
- 原始 CPU/GPU 数值仍标为“该帧边界读取的引擎计时”，不能改标为同一帧精确归因，因为这些计时独立发布且 GPU 有延迟。
- 增加有容量上限的事件缓冲，记录开始/结束时间、开始/结束帧号、阶段、配方键与父事件 ID。缓冲截断或跨越记录边界要显式标记，不能静默当成完整采集。
- 重置/停止记录时维护采集代次，避免把清空前开始的事件拼接到清空后的统计。

### 1.2 覆盖图标与掉落物预览

改动：`ColdSteelWeaponIcons.cpp`、`ColdSteelPickupStudio.cpp`、`ColdSteelPickupWeapon.cpp`；必要时新增一个小型计时辅助文件。

- 第一版记录整个图标 Tick，以及 `Prepare`、视觉初始化、配件/包围盒准备、`Warm/BuildWeapon`、Capture 提交、Readback 的执行时长与次数。
- 同时记录队列长度、当前配方、阶段、缓存命中、完成/失败/延期次数。区分“本帧执行了多少 ms”与“任务已经等待了几秒”。
- 预览场景通过所属 GameInstance 的游戏 World 上报，不能使用预览角色的 `GetWorld()` 查找面板子系统，否则仍会漏记或记到错误的 PIE 实例。
- 嵌套阶段显示包含关系：`Prepare` 已包含 `Warm`，两者不能再次相加成为总成本。
- 在相同位置添加 UE CPU Trace scope，供以后已有或新保存的 Insights 文件进一步查看；不为此启动采集。

### 1.3 面板展示与导出

改动：`DevelopmentPerformancePanel.cpp`、`DevelopmentPanelWidget.h/.cpp`、`FPSPerformanceMetricsExport.cpp`。

- 在现有性能页增加“长帧事件”和“后台图标任务”两块紧凑信息，不另建一套面板。
- 将现有“武器重建”明确标成“玩家身体路径武器重建”，图标/掉落物初始化分别列出；未埋点显示“未采集”，不能用 0 代替未知。
- JSON 升级为 schema 3，保留 schema 2 的汇总字段，新增原始帧、事件、计量范围与截断信息。
- 原始记录变多后，主线程只复制不可变快照；序列化和写盘使用不访问 UObject 的后台任务。完成后回主线程更新导出状态。
- 记录快照生成和导出提交事件。导出完成耗时可写入输出元数据，但不能假装它属于导出之前的采样窗口。
- 保留冻结、清空、记录开关语义；采集不依赖性能页是否显示，显示层仍按现有低频刷新，不每帧创建列表。

批次 1 的完成口径：导出结构能呈现本次暴露的后台工作及长帧关联。代码接入完成与运行表现由用户实际使用后确认，不能因加了埋点就宣称根因已全部定位。

## 批次 2：处理图标生成的阻塞

### 2.1 按实际需求调度

改动：`ColdSteelInventoryWidget.cpp`、`ColdSteelItemTooltip.cpp`、`ColdSteelEnhancementWidget.cpp` 及图标子系统。

- 继续使用现有目录图作为实时图标完成前的显示，保留现有 64 项缓存、Pending 去重和配件配方键。
- 背包/仓库按实际打开状态和可见条目提交需求；提示框与强化面板保留自己的请求来源。一个界面关闭时不能取消另一个界面仍在使用的任务。
- 优先处理当前可见、选中或正在交互的物品；离屏任务降优先级或移出未开始队列。
- 配件变化后用新配方请求；旧任务晚完成只能写入自己的缓存键，不能覆盖当前配方的显示。

### 2.2 图标与掉落物共享最小视觉装配

改动：`ColdSteelWeaponIcons.cpp`、`ColdSteelPickupStudio.cpp`、`ColdSteelPickupWeapon.cpp`；新增共享的预览配方/装配模块。相关武器模块只提取必要的展示数据与装配逻辑。

- 将网格、静态展示所需姿态、可见材质区段、实际配件、变换和包围盒组合成共享装配结果。
- 图标路径逐步退出完整 `AFPSGAMECharacter::InitializeWeaponVisuals`：不初始化开火逻辑、音效、特效或静态展示不用的换弹/战斗动画。
- 先按武器定义解析需要的资源，去掉“先加载 AKM，再覆盖为目标武器”等无关依赖。实际使用的姿态、配件、材质和构图仍沿用当前规则。
- 图标准备得到的装配数据和包围盒直接进入掉落物缓存；移除图标 Prepare 中为了预热而再创建 Pickup、另一套角色、随后销毁的流程。
- 掉落物消费共享结果，保留自身坐标对齐和碰撞尺寸规则。不能直接把图标相机坐标下的包围盒当作掉落物局部包围盒。
- 提前准备可能用于丢弃的配方，并在交互时提高优先级。若冷启动时尚未就绪，不能在鼠标松开时悄悄退回完整同步初始化；该边界要沿用库存事务规则处理，不提前扣除物品或重复生成拾取物。

这一批的实际目标是避免重复角色初始化。不能只删除 `Warm` 调用，将首次等待转移到丢弃操作。

### 2.3 将资源与渲染准备拆成可让出帧的步骤

建议阶段：

```text
请求配方 → 异步加载依赖 → 等待网格/材质/纹理就绪
         → 分步装配与包围盒 → 提交 Capture
         → 提交 GPU 回读 → 后续帧查询完成 → 转换/缓存/通知界面
```

- 资源加载使用本机引擎已有的 `FStreamableManager::RequestAsyncLoad`，异步句柄和资源引用保留到任务完成。
- 资源加载完成不等于资产编译和渲染资源就绪，分别检查；等待阶段让出帧，不调用全局 FinishAllCompilation 或同步 flush 来强行完成。
- UObject/组件创建和修改仍在游戏线程完成，按步骤安排工作；不能把整个现有 Prepare 直接扔到后台线程。
- CPU 蒙皮顶点包围盒计算按同一配方缓存，必要时分批遍历。只在步骤边界检查预算不能限制单个大步骤，所以耗时段本身也必须拆开。
- 使用 `FRHIGPUTextureReadback` 提交读取，后续帧通过 `IsReady` 判断完成，再取数据。取消任务时等待已提交 GPU 操作完成后再释放资源。
- 保留 HDR/透明度转换、尺寸和纹理上传规则，避免异步化导致颜色、透明边缘或配件显示变化。
- 初始调度预算属于待测参数，不写成“必定每帧低于 1 ms”的保证。继续用批次 1 的阶段计时记录实际结果。

## 批次 3：持续帧率另行归因

约 54 ms 的典型帧时尚无足够分项，后续首先查看 Game 内部的游戏 Tick、Slate/编辑器、动画、物理与项目自定义工作。若只有现有汇总，就保持为未定位，不凭组件三角数选择优化对象。

以后由用户运行时，可关注三个现象：首次进入/打开背包、连续切换武器配方、立即拖拽丢弃。输出同场景窗口的原始帧与阶段计时，观察长卡顿是否消失，同时确认图标外观、配件和库存/拾取行为。此处是后续观察口径，不自动执行测试或启动 UE。
