### 1. 优先定位 Game 线程一侧的持续耗时

两份 Game P50 与帧时间 P50 几乎一致，GPU0 的典型值明显更低，Game 的已记录等待中位数接近零。证据优先指向 Game 线程一侧，而非 GPU 持续满载。这里的 Game 是引擎进程级时间，PIE 中包含编辑器相关工作；不能直接归因到玩家、天气、动画或某一个组件，也不能等同于整个 CPU 的使用率。

Draw 的等待约 59–60 ms，不代表绘制命令本身花了这么久。引擎将 Draw、等待和含依赖等待的关键路径分开统计，不能把它们简单相加；异步计时也不能拿不同指标的 P99 拼成一个具体帧。B 的 Draw 峰值 306.51 ms 是额外长帧线索，但目前无法与 Game/帧时间峰值逐帧对应。

60 FPS 的预算为 16.67 ms；两份所有帧都超过 33.34 ms。即使去掉各自最慢两帧，剩余均值仍约 56.07 / 56.65 ms，说明持续低帧与偶发长卡顿同时存在。这个去极值计算只是解释数据，不是正式优化后的 FPS。

### 2. 长卡顿是真正需要单独追踪的问题

两份最大帧时间均为 1065.37 ms，证明当前文件能保留超过 125 ms 的帧间隔。由于窗口重叠，完全相同的峰值很可能来自同一帧；缺少峰值帧 ID，不能确定，也不能将它数成两次卡顿。

在 160 / 157 个样本和 nearest-rank 算法下，P99 恰好都是各自第二慢的样本。它能说明有严重尖峰，无法稳定代表长期尾部表现。GC、同步加载、资源导入、着色器/PSO、UI 操作、文件写入或等待都只是待核对方向，不能从当前汇总认定原因。导出使用主线程同步序列化和写文件，本次快照在写文件前已缓存，因此不能解释本份快照过去的帧，但可能影响后续窗口；目前也没有导出耗时/事件标记。

### 3. 已计量的扫描与文本更新不是几十毫秒耗时的解释

A/B 各记录 18 次快照构建和 17 次 UI 更新，两项窗口累计分别约 12.54 / 12.62 ms，折合每个引擎帧约 0.078 / 0.080 ms。它们不是每帧各执行一次。

这只覆盖快照构建与 UI 数据更新，未包含采样回调本身、完整 Widget Tick、Slate 布局/绘制、模糊和导出 I/O。因此可以说“已计量的两段开销较小”，不能说“整个面板总成本只有 0.08 ms”。

## 原先的嫌疑应如何调整

- 当前埋点范围内，两个窗口的可见性字段变化、武器重建、服装重建均为 0；不能继续把这些路径的频繁重建认定为这两份低帧数据的主因。范围仍仅是已埋点的玩家身体路径。
- 装备采集、角色可见性刷新、世界可见性刷新均为每窗 42 次，约 4.06 / 3.98 次每秒。它们值得补耗时，但次数本身不能说明昂贵。
- 骨骼组件 8 个、带资产 7 个、启用 Tick 且已注册并带资产的 3 个；AlwaysRefresh 配置 7 个，其中满足 Tick 条件的 2 个。603 是资产骨骼总数，不能解释为每帧实际计算 603 根骨骼。实际动画 Update/Evaluate 和手动刷骨仍未知。
- Niagara 40 个组件、2 个激活，只有数量，没有模拟或粒子耗时；不能据此认定特效很便宜或很昂贵。
