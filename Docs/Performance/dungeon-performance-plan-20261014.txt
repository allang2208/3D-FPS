地牢性能排查与优化实施方案
日期：2026-10-14
项目：D:/FPS3D/FPSGAME

结论

本次持续低帧以 GPU／渲染流水线为主要方向；刷怪后的动态角色工作集是第一排查对象。现有分帧生成和预热只搬动首次创建成本，无法解决已经激活的几十只怪物每帧仍然昂贵的问题。
代码中另有一项明确的准备队列优先级缺口：远房占满两个准备名额，当前战斗区域几乎没有命中预准备。它值得先修，但不能承诺单独解决 100–150 ms 的 GPU 高耗时。
本轮交付为已有导出的离线分析、当前源码排查和实施方案。没有修改运行代码、资产、画质或刷怪规则，没有启动 UE、编译或新增运行测试。

二、系统机制与代码发现

1. 两个大厅属于同一启动区域，分帧生成并不限制持续负载

FacilityHallEncounter.cpp:563 的 UpdateEncounter 以 Theme->HasStarted() 为生成条件。PlayerInHall 只更新探索状态，并非刷怪开关。
本次 1 号迎宾大厅和 2 号分流大厅首次生成相隔 0.172 秒，首波分别 16 和 18 只，合计激活 34 只。资源样本随后记录 33 活怪、1 死怪；整次观察峰值 37 活怪。
FacilityHallSpawnSubsystem.cpp:90 起保持全局一次尝试与 50 ms 间隔，每厅约 200 ms 请求。它缓和创建叠加，却不会限制激活后的动画、蒙皮、阴影和光追工作。
结论：双厅同步是现有区域玩法，不标为程序错误；默认保留数量和波次规则，不用延迟开战、限制攻击人数或删除屏幕外敌人充当优化。

2. 两个准备名额被无关房间占住，存在明确的调度优先级缺口

时间线以第一波开始为 0：
- -7.83 秒：room=1 slot=4 准备接待员。
- -7.66 秒：room=61 slot=3 准备接待员。
- +0.70 秒：room=1 准备实例被激活，预热 submitted=1、gpu_complete=1。
- +0.79 秒：空出的名额给了 room=55 slot=0 的螳螂。
- 后续准备容量持续被占用；本次第一波 34 次激活只命中准备 1 次，第二波 15 次全部未命中。

直接代码原因：
- FacilityHallEncounter.cpp:567 在检查主题是否开始之前请求准备，未限制当前/近期区域。
- FacilityHallSpawnSubsystem.cpp:74 先判断 PreparedCount>=2，然后取 PreparationPending[0]；没有战斗区优先级，也没有替换不相关准备项的策略。
- FacilityHallEncounter.cpp:666 按各房 NextSlot 查找可准备槽位，未按预计激活时间过滤。
- FacilityMonsterGpuWarmup.cpp:86 超过五秒只停止新的捕获提交，并不会自动退还 Actor 准备名额。实例可以继续合法等待，但不应永久挡住当前区域。

这是吞吐与准备命中率问题，不是证据已经确认的全部 GPU 卡顿根因。首波窗口 SpawnAttempt 累计 91.27 ms，最大 25.17 ms；第二波累计 26.64 ms，最大 2.25 ms。不能把这类同步调用累计值解释为随后每帧 140 ms。

3. 员工身体的持续变形与光追路径需要精确归因

资源历史实际观察：接待员 LOD0 162,110 顶点，研究员 LOD0 119,791 顶点，每个网格 6 个 section；第一波低帧段有 12 接待员和 6 研究员，共约 266 万个源 LOD 顶点。两类员工观察峰值 27 只。
这些顶点是已观察网格规模，不等于每帧实际提交或执行顶点总数。安保、投手、精英还需另计；详细 Morph 观察目前只覆盖上述两类。
多数每只两个活动 Morph，而保存的 Morph 库分别有 181 和 231 个。两种压缩输入按资产共享，总逻辑大小约 69.17 MiB，不能乘以实例数量。所有已返回的 RT SkinCache separate 标志为 false，不支持声称正在持有两份独立蒙皮输出。
本次实际渲染 LOD 均为 0；报告没有完整资产 LOD 链，不能只凭这项断言磁盘资产当前只有一个 LOD。

引擎源码 E:/Program Files (x86)/UE_5.8/Engine/Source/Runtime/Engine/Private/SkeletalRenderGPUSkin.cpp：
- :849 已有 IsMorphUpdateNeeded，不能再把“相同 Morph 不更新”当成缺失的基础机制重造一遍。
- :1772 Scatter 跳过权重为零的 Morph，只对活动批次派发。
- :1826 Normalize 按整个 Morph 输出缓冲的顶点数派发。因此活动曲线少不代表大型网格的 Morph 路径一定便宜。
- :2968 RT LOD 受已有 LOD 范围限制；没有低 LOD 时，仅调偏移不会产生更轻几何。
NurseZombie.cpp:65 强制 AlwaysTickPoseAndRefreshBones。该选择还服务于命中、碰撞姿态和倒地恢复，不能按“看不见”直接关闭全部动画。

这些代码与数据使 Morph/SkinCache、动态 BLAS、角色阴影成为优先候选。最新 JSON 没有 GPU pass 时间，尚不能判定三者的耗时排序或归责单一模型。
Epic 官方也将高面数变形骨骼的动态 BLAS 更新列为高成本来源，并提供 Ray Tracing Min LOD。这个机制依据不等于本次已经量出的瓶颈：
https://dev.epicgames.com/documentation/unreal-engine/ray-tracing-performance-guide-in-unreal-engine
https://dev.epicgames.com/documentation/en-us/unreal-engine/skeletal-mesh-rendering-paths-in-unreal-engine

4. 现有 GPU 预热范围有限，而且本次命中率低

FacilityMonsterGpuWarmup.cpp:38–55 只准备实际身体；:94–105 捕获关闭光追、阴影和 Lumen，64×64 捕获主要覆盖光栅蒙皮/Morph。
它没有预热完整动态光追和场景阴影，也不降低后续每帧的必要成本。保留小容量和显存余量门槛，不扩大为整波隐藏实例池。

5. 房间可见性存在继续收敛的空间，但不是已确认的首要毫秒来源

最终快照 427 灯，其中 349 启用、272 带阴影；视锥球形候选只有 25 灯、15 阴影灯。不能宣称“349 灯全部同时画出来”。
AuthoredDungeonLighting.cpp:172–193 通过全相机视锥遍历门户，没有逐门缩小可见锥，也没有在此处读取门叶实际开闭；这是保守候选，可能保留遮挡之后的远房。
AuthoredDungeonGenerator.cpp:442 的 ISM 分组按 40 m XY 网格与材质/碰撞等键聚合，不包含楼层 Z 或房间身份；AuthoredDungeonLighting.cpp:245 采用所属房间并集，一房需要则整组保留。
目前房间灯光/几何调度本身在最终十秒的包含时间约 12.38/7.07 ms，不是每帧该耗时。优化目标应是它保留的渲染工作，而非为了省这点 CPU 重写调度器。

6. 旧的 CPU、物理和资源优化已经在当前代码中

- MonsterBTNodes.cpp:162 已有按 owner 固定相位的 10 Hz 知识更新。旧方案中“尚未错峰”的描述已过时。
- MonsterAIController.cpp:232 已有 0.65 秒寻路节流和目标位移门槛；MonsterNavigationCache 已有同帧投影缓存。
- FatZombieAnimInstance.cpp:153 已在过渡结束后裁掉旧姿态分支。
- HumanoidRagdollBudget.cpp:10 已有 8 模拟对象/128 刚体/4 尸体准入预算与冻结尸体 LOD 更新；本次采样同时模拟身体峰值 4。
- r.PurgeEditorSceneDuringPIE=1 已在最新导出回读到，不能重复列为未实施项。
- 图标队列停在 ItemPanelClosed，最终窗口无图标生成动作；不能因队列有 38 项就认定后台在连续捕获。
- 最终十秒 World.Tick 包含时间约 1261 ms（每帧约 9.0 ms），Slate.TickAndDrawWidgets 约 527 ms（每帧约 3.77 ms）；Slate 内含 WindowPaint 与可能嵌套的 HUD，不再重复求和。存在局部长帧，但不足以单独解释持续 GPU 约 70 ms。

7. 显存与加载分别处理

247 个、至多 2 Hz 被动显存样本均未报告超预算，最小可用余量 377.67 MiB。余量仍紧张，且采样可能漏掉瞬时换页；本次不能沿用旧记录“超预算数百 MiB”的结论。
缺少本次资源详采及逐资源驻留事件，无法把压力精确分给 VSM、纹理、动态 BLAS 或 SkinCache。
地牢准备总计 74.18 秒，其中布局工作线程 8.45 秒，资源依赖等待跨 1791 个装配 slice，最大 slice 90.90 ms。这是进入阶段的独立问题，不能拿来解释后面战斗中的持续低帧。

三、按优先级实施

第一批：修正原准备队列的当前区域优先级

修改范围：FacilityHallSpawnSubsystem、FacilityHallEncounter、FacilityMonsterGpuWarmup，以及已有 F6 生命周期事件。
- 请求携带区域/槽位身份与预计激活优先级；当前已开始区域的未生成槽位优先，随后才是即将进入的相邻区域。
- 两个准备名额优先分配给当前双厅待激活槽位；回收离当前区域无关的准备项，沿已有 DiscardPreparedMonster 收尾，不触碰已激活角色。
- 避免立即重新加入被淘汰的远房，使用状态变化触发或低频重评；保留预算不足时的正常生成回退。
- F6 记录准备房间/槽位、等待年龄、替换原因、预热阶段和命中/未命中原因，使名额是否用在当前波次上可见。
- 保留原种子、槽位、位置随机流、生成节奏、任务精英身份、AI/BeginPlay 激活时点；客户端准备不控制服务端波次。
收益范围：提高有限准备资源的有效性，降低首用/激活峰值；不承诺根治持续低帧。

第二批：按同次 GPU 分项选择持续开销的实际改造

先复用已有自动刷怪采集入口保留完整首波后至少 20 秒，覆盖 Morph Scatter/Normalize、SkinCache、动态光追几何更新、VSM、Lumen，以及 GPU 队列间依赖。CPU 侧同时记录 AI、动画后台任务、Slate 和渲染等待。此项是后续测量计划，本轮没有启动。
不在战斗测量窗口内执行重型全量 RHI 枚举。资源清单可单独采，保留其观察开销；最新 JSON 本身不能替代 GPU pass trace。

根据分项选择：
A. 若 Morph 为主：先查反复更新是否来自真实曲线变化、状态切换或组件重建；引擎已缓存相同输入，不重复加一层无效缓存。若衣物变化只影响局部顶点，再做单个员工的局部 Morph 输出候选，维持原网格细节与衣物纠正。拆衣物需计入额外组件、材质提交、骨骼传递和光追结构成本，不直接全员拆分。
B. 若动态 BLAS 为主：先去掉确实不贡献当前视图/反射/GI的重复或无效更新。需要更轻 RT 几何时，先准备单种员工的独立 RT LOD 候选；保留主视图 LOD0。RT LOD 变化可能增加另一份蒙皮输出并影响反射轮廓，要看净成本，不能直接全局设置 LODBias 或关闭硬件光追。
C. 若 VSM 为主：依据具体灯和移动角色的页失效范围处理阴影贡献及边界，保持近景主灯与必要遮挡，不按“地板”或“远处”批量关阴影。
D. 若驻留/驱动等待为主：按同次资源所有者回收不再使用的预览或远房渲染资源，拆分渲染驻留与碰撞/导航/任务依赖，保留共享引用。不要扩大纹理池、强制 GC 或清 DDC来代替归因。

第三批：收敛地牢渲染工作集

修改范围：AuthoredDungeonLighting 与 AuthoredDungeonGenerator 的现有模块注册、门户和实例分组。
- 门户传播使用父级已裁剪可见域，结合实际门状态；保留邻房、快速转身恢复、阴影/GI/反射边界和隐藏滞后。
- 只对确实跨楼层/跨遮挡区的共享 ISM 增加楼层或房间簇分组，保留必要合批；不要一实例一组件或整房破坏性合并。
- 加入 Wanted 房间数、各保留原因、跨房 ISM 数等已有采样摘要，说明为何房间仍被保留。
- 多人使用各本地视图的呈现需求；服务端碰撞、追击、搜寻、任务/门锁和存档继续独立存在。现有单人剔除不能直接作为全局联机状态。
收益范围：降低无贡献区域的持续渲染与资源压力；需避免门口露空、漏光和反射缺物。

第四批：按剩余 CPU 热点精修

保留已有错峰、导航缓存、尸体预算和特效池。只对同帧且输入版本未变的重复 UpdateKnowledge/战斗属性查询去重；受击、目标失效、状态转换立即失效缓存。
NurseZombie::Tick 仍承担攻击接触和恢复时钟，不整体降 Tick。若需要动画表现分级，先分离命中/碰撞所需骨骼与纯呈现，并覆盖背后攻击者、正在施法、倒地和联机副本。
F6 快照扫描移到已有低频缓存或分批采集可降低观察干扰，但不把它作为当前 GPU 持续低帧的主要修复。

有画质取舍的后备选项

中远距离显示 LOD、动画降频、RT 代理精度、阴影更新频率属于可见效果取舍，单列候选；默认保留当前模型与动作。关闭 Lumen/光追、减少怪数、推迟第二波、缩小分辨率、提前消尸不列入首批保表现优化。
Mass/VAT、整套 Actor 池、引擎渲染器重写也不作为当前第一步。

四、将来由用户运行的对照口径

同一构建、种子 1106641440、机位/相机路线、2552×1222 与实际内部渲染比例、画质、前台状态和 F6 开闭状态。分别记录进入、首波、第二波与尸体/技能叠加；PIE 和独立运行分开比较。
同时看帧时间 P50/P95/P99、50/100 ms 慢帧数、CPU/GPU 分项、实际怪物类别数量、准备命中率和显存余量；不以平均 FPS 一项代替。
60 FPS 对应 16.67 ms 帧预算，可作为目标，当前没有证据承诺哪批能达到。玩法对照包括波次总数、触发、精英开门、命中/受击、尸体接地、联机共享进度。
以上测试尚未执行。当前最适合先实施的是准备优先级修正，同时用现有采样补齐持续 GPU 成本；后续按实测主项选择第二批分支。
