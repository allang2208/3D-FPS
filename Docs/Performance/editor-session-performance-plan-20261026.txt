开发顺序

第一阶段：先把已有证据按成因分开
- 复用本次 UE 时间线，分别统计战斗、同步加载、GC、编辑器模态窗口；在同时间窗内解释 GPU/CPU 等待。
- 解析已有 WDDM ETL 的实际覆盖范围，再对齐 PID、adapter、QPC 与缓冲生命周期。512 MiB 是循环文件，events_lost=0 不保证起始事件未被覆盖。
- 本次是快态的完整驻留/调度证据；旧慢态没有 WDDM。只在现有证据不能区分原因时，后续由用户在同配置、同种子、同路线下补一个慢态窗口，不再重复普通 JSON。
- 必要元数据接入已有 F6 的事件与有界快照：进程/PIE 生命周期、二进制版本、地图种子、实际视口、编辑器模态状态。不要新建第二套常驻全场采样器。
完成标准：每个重点停顿能落到具体调用/等待区间，缺失的硬件证据单列，不把“数据更多”当作修复。

第二阶段：处理编辑器会话与资源生命周期
- 沿现有 GameInstance、World、房间和准备拥有者的释放点，查退出 PIE、重新进地牢、换装、取消准备后的强引用及实际资源数量变化。
- 重点入口：FPSBodyAssetPreloader、PlayerSkillRenderPreparation、DungeonCombatEffectPreparation、DungeonGlassRenderPreparation、AuthoredDungeonGenerator 清理路径、FacilityHallSpawnSubsystem 回收路径。
- 这些模块已做过一轮治理，本阶段只修仍被证据证实的遗留拥有者、重复注册、取消未清理或过期保留；不重新堆一套缓存/池。
- 保留当前场景、当前装备、画面和战斗所需资源。正常缓存允许稳定占用；退出一次场景后仍非零不是泄漏证据，要看同条件重复运行是否持续增长和谁仍持有。
- 准备池沿用 16 实例/256 MiB、现有 CPU/GPU 预算与释放语义，不靠取消余量限制强行命中。
完成标准：同条件重复进入后的资源进入稳定范围，并能解释保留项；退出和取消路径不遗留活动工作。运行确认由用户完成。

第三阶段：定向处理实际的首刷加载/CPU 尖峰
- 先查清模态窗口的来源及触发入口。若是项目作者工具/导入监听，在 PIE 期间暂缓作者操作，并在退出后恢复；如果是必要用户交互则如实标记，不隐藏对话框。
- 对确认属于游戏的同步加载，将必要依赖接入现有进入准备流程；不把整个素材库常驻。
- 减少重复对象创建与失效引用，按已有加载阶段安排必要清理。默认保留自动 GC，不通过战斗时强制 GC 或全局拉长 GC 周期掩盖内存问题。
- 仍保留生成尝试、正式激活和后续动画/渲染的时间边界；生成函数快不代表整帧快。
完成标准：消除已定位阻塞的调用入口，不将编辑器对话框时间计作怪物收益。

第四阶段：建立独立游戏进程的性能基线
- 日常功能开发继续在编辑器；正式性能比较使用固定配置和路线的 Development 游戏构建，减少编辑器工具/预览的混入。
- 先检查现有 Cook/依赖是否具备可运行产物；仅编译 Game EXE 不等于已打包。需要制作时完成后台 Cook/Stage，分开报告编译、资源和运行状态，不自动运行测试。
- 不把换成独立进程称为游戏性能已修复；同样跟踪长会话/重复进出后的稳定性。
- 最后才针对剩余实测 GPU pass 和 CPU 热点优化；维持画质、怪物数量、动作频率、光追/Lumen 与战斗规则。暂不迁移 Mass/Animation Sharing/GPU crowd，也不以关闭渲染功能换取表面帧率。
完成标准：用户能够复现同一基线，分别评估持续帧时间和首刷尖峰；先防止回到个位数帧率，再评估稳定 60 FPS 的成本与可行性。

日常启动建议
普通开发不需要长期依赖管理员权限；现有脚本保留给 WDDM 调查。
性能对照时固定启动方式和进程状态，完成导入/编译后再测。重启可作暂时恢复和对照手段，不能代替生命周期修复。
若要单独确认权限因素，后续只比较“新启动普通权限”与“新启动管理员权限”的同一场景，不拿旧会话与新会话直接比较。此方案不自动启动这项测试。
