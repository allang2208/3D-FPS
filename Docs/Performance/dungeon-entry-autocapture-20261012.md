# 随机地牢自动采样：2026-10-12 晚间

本轮按用户要求定位短暂卡顿，提前挂采样，在用户自行进入随机地牢后自动记录。没有改变画质、怪物数量、游戏逻辑，没有启动或停止编辑器/PIE。

## 证据与条件

- 原始数据：`Saved/DungeonEntryCaptures/20261012-113959-502728/`。
- `capture.utrace`：Unreal Insights CPU、GPU、Frame、资源加载、Bookmark 等轨迹。
- `capture.json`：采样状态、窗口前后台、暂停、怪物数量、相机、画质配置；最终 `complete`，`errors=[]`，Trace 正常停止。
- `adapter-samples.csv`：约 1 Hz、整张显卡的 NVIDIA 利用率和显存占用。
- `process-gpu-memory.csv`：Windows GPU Process Memory，限定 UE PID 12744。Dedicated/Local 是同类计数，不能相加；Committed 不是物理驻留显存。
- `analysis.json`、`hitch-details.json`、`frames.csv`：离线分析结果；`analyze_capture.py` 可重新生成分段统计。
- 录制北京时间 19:43:27–19:45:07，共约 100 秒；2552×1222，RTX 3080 Ti 12 GiB，硬件 Lumen、虚拟阴影、阴影质量 3。
- Trace 中 `StartTraceToFile` 结束时间 507.165343 秒作为相对零点；剔除录制前尾缓冲和未结束事件。
- 录制前半有加载和切后台，只分析相对 61.1–100 秒、持续前台且未暂停的游戏段。Python 回调间隔不是引擎帧耗时。
- 第一波从约 69.4 秒开始，约 72 秒达到 25 只存活怪物；88 秒后第二波开始加入，99 秒前最高观察到 29 只存活。游戏日志明确记录 `FacilityReceptionHall wave2 triggered`。

## 已确认的主要等待链

1. 相对 74.728 秒：一帧 **356.273 ms**，`Sync_RenderingThread` **343.542 ms**，该帧所有 `UWorld_Tick` 合计约 **6.245 ms**。渲染线程先等待可见性任务约 178.8 ms，又等待遮挡结果约 174.1 ms；工作线程明确记录 `GPUBound_WaitingForGPUForOcclusionQueries_SeeGPUTrack` / `RHIGetRenderQueryResult_GPU_Wait` **174.270 ms**。附近 GPU Graphics 帧跨度 **340.423 ms**。
2. 相对 92.020 秒、第二波期间：一帧 **284.338 ms**，`Sync_RenderingThread` **258.796 ms**，`UWorld_Tick` 合计约 **19.498 ms**。工作线程等待 GPU 遮挡结果 **182.002 ms**，渲染线程随后另一个场景渲染还等待约 90.4 ms。
3. 两段附近 D3D12 提交线程 `FD3D12Queue::ExecuteCommandLists` 分别出现 **97.352 ms**、**76.463 ms** 峰值。当前引擎该作用域包住 residency manager 和实际队列提交，不能只凭它区分显存换入、驱动提交和其他等待。

因此主要长停顿已定位到 **GPU/图形提交阻塞，进而使渲染线程和游戏线程等待**。本次最长卡顿不是 AI 寻路、怪物逻辑或垃圾回收在游戏线程直接占满几百毫秒。遮挡查询是等待点，不足以认定应关闭遮挡剔除。

## 显存压力：强线索，尚不是唯一根因证明

- 整卡占用在刷怪前后约 **11.2–11.3 GiB / 12 GiB**，活跃游戏段 GPU 利用率大多 **93%–97%**。
- UE 专用显存约 **10.0 GiB**，刷怪前共享 GPU 内存约 **1.0–1.1 GiB**。
- 第一波后的停顿附近共享内存升到 **1.75 GiB**；第二波附近最高 **1.85 GiB**。
- UE GPU committed 由约 **13.05 GiB** 升到约 **14.15 GiB**，但 committed 含非驻留/系统内存，不能与 12 GiB 物理显存直接相减当作“爆显存量”。

资源占用增长、D3D12 提交阻塞和 GPU 等待同时出现，支持优先排查显存余量与资源驻留抖动。采样频率约 1–1.5 秒，尚不能量化哪一次换页造成某一帧的全部停顿，也没有将驻留开销归属到唯一纹理或网格。

录制结束后用户已正常关闭 UE（日志 19:47:51 正常退出）。因此补充的 `ListTextures`/Groom/SceneCapture 实时清单没有取得；没有为补清单重新打开编辑器。`inspect_resources.py` 只是未执行成功的读取脚本，不是已有资源清单。

## 生成与模型成本

- 第一批两只怪物所在帧 `FacilityHallEncounter` 合计 **70.478 ms**，整帧 **86.812 ms**，确有首次实例化峰值。但后续 284/356 ms 停顿的主要时间在等待渲染，单纯把刷怪循环变慢不足以解决。
- 74.55 秒附近还有武器切换的 `FlushAsyncLoading` / `GUNPLAY_FX_READY` / `GUNPLAY_ADS_CALIBRATED`；相邻帧 151.5 ms，包含消息处理和世界 Tick 开销。不能把这一组资源冷启动都算到怪物。
- GPU Graphics 的非 Nanite 虚拟阴影作用域，生成后平均约 **2.60 ms/帧**、第二波约 **2.79 ms/帧**。这反映常态渲染负担，不能单独解释数百毫秒停顿。
- 此前读取的三类员工模型只有 LOD0、阴影和光追开启，属于后续资产优化对象；面数和顶点数不能替代实际 GPU 耗时归因。
- 本轨迹也包含 Hair、Lumen、TSR 等开销，Hair 在怪物出现前已经存在，不能直接认定是这三类员工的头发。
- GPU 作用域是时间跨度，包含队列空隙、抢占或同步。Graphics 和 Compute 并行，不能相加；不能把被拉长的 `FXSystemPreRender` 235.7 ms 宣称为特效着色器纯执行耗时。

## 后续优化优先级

1. 先取得当前进程的资源分类和最大资源清单，结合显存预算，减少不必要常驻资源和突发申请。现有配置已经是 30% 纹理池比例且限制 VRAM，不能再盲目扩大纹理池。
2. 对员工模型做有明确距离阈值的 LOD、阴影和光追几何成本控制，保留近景质量。只修改资产前，须先确认主要资源占用；当前数据不支持“一律砍半面数就能解决”。
3. 单独处理约 70 ms 的首次实例化，以及武器首次切换资源准备，避免与波次增长叠在一起。不要用全部怪物预生成常驻的办法继续挤占显存。
4. 优化效果需相同分辨率、视角、种子和波次的用户复测；本轮只交付测量和定位，没有宣称帧率问题已修复。
