现有随机地牢：刷怪卡顿与 40–50 只怪物调度方案
日期：2026-10-13
状态：当前源码与既有记录的分析、实施计划；本次没有修改运行代码、资产或配置，没有启动 UE、试玩或新测试。
范围：沿用 D:/FPS3D/FPSGAME 和当前随机地牢，不新建地图、副本、工程副本或第二套刷怪系统。

一、决策

优先顺序：补齐实际怪物资源准备范围 → 找出并释放闲置资源，留出战斗显存余量 → 在现有刷怪队列内分阶段提前准备 → 多怪物周期任务错峰、去重 → 根据剩余热点决定动画/衣物处理。
这几项收益针对不同瓶颈，不能用“池化”或“降低 AI Tick”替代全部工作。
先做准备一次、激活一次的实例生命周期；完整的死后回收再利用放到后面。后者重置成本、引用与玩法风险更高，目前没有证据证明它比显存驻留治理更值得优先做。
保持模型、贴图、衣物修正、Lumen/光追设置、怪物数量、波次触发、攻击与受击规则。下面的收益等级表示针对当前证据的预期优先级，不是已测得的 FPS 增幅。

二、目前能确认什么

1. Saved/PerformanceDiagnosis20261013-1004/diagnosis.txt 分析的两份 F6 JSON 来自同一次运行，相隔约 2.93 秒，不是两次独立复测。
   1704×982、RTX 3080 Ti、PIE。首批出现前区间约 64.55 FPS；出现后若干秒降到约 11.65–13.02 FPS；稍后恢复。
   首批阶段进程显存 UsedLocal=11.239 GiB、BudgetLocal=10.623 GiB，超预算约 632 MiB；包含编辑器资源。
   这支持显存压力参与问题，但没有逐资源驱逐/换页事件证明它解释了全部低帧；后续部分低帧样本没有超预算。
   同次日志实际生成过 36 只首波怪物，资源采样仅统计其中两种员工。眼前十几只不能代表整个地牢的负载。
   当前源码新增了随机迎宾精英，因此 36 只是历史记录，不代表修改后固定数量。

2. 之前详细 GPU trace 存在 MorphUpdate / Normalize / Scatter 和蒙皮开销。其分辨率为 2552×1222，不能与新 JSON 直接比较优化百分比。
   最近样本绝大多数每只只有 2 个活动 morph；不是数百个形变同时执行。
   两种网格的约 69.17 MiB 压缩 morph 输入按资产共享，不能乘怪物数量。每实例变形输出、蒙皮、光追结构和纹理仍需分开归因。
   那次 118 ms 纹理分配没有在后续记录中复现，不能继续把所有卡顿归为同一个调用。

3. 现有优化应保留：
   - FacilityHallSpawnSubsystem：全世界共用生成入口，每帧最多一次尝试、全局至少 50 ms，每大厅原有 200 ms 请求节奏；异步轮询渲染注册 fence。
   - AuthoredDungeonGenerator / DungeonMonsterRenderPreparation：类异步加载、未注册组件的 PSO 准备；22 个材质用途标志已经按先前回执保存。
   - FatZombieAnimInstance：结束过渡后停止旧动画分支的冗余计算。
   - MonsterAIController：过滤同类感知，已有 0.65 秒导航请求节流与目的地变化判定。
   - MonsterAwareness：群体警觉已有每帧最多两次广播预算、单跳传播和去重。
   - HumanoidRagdollBudget：已有 8 个模拟对象 / 128 个刚体 / 4 个尸体模拟的默认准入预算，活体倒地优先；稳定尸体会冻结。
   - 冻结尸体保留姿态及查询碰撞，并已有 LOD 更新入口。不是所有尸体持续执行物理。
   - FPSImpactFXSubsystem、FluidPresentationSubsystem：已有特效预算/池，不另建重复管理器。
   - ColdSteelPickupStudio：辅助枪械装配角色 LRU 上限；WeaponIcons 空闲释放捕获资源；完整预加载模式中已增加非活动纹理保护回收。
   - HUD 共享查询等已有热路径修订，以及 F6 的资源历史记录。

三、发现的直接衔接问题

1. 随机精英已经加入 FacilityHallEncounter::PreparationAssetPaths(RunSeed)，但 AuthoredDungeonGenerator.cpp 的 MonsterRendering.AddClass 仍按 MonsterClassPaths() 的固定四类过滤。
   当选中另外一种精英时，它的类可以已经载入，却未进入这一批专门的怪物 PSO 准备。
   应用同一份“本局实际候选资源清单”驱动加载和渲染准备。不能仅删除过滤条件：现有模板提取只特判 Nurse/Wolf/Bellow，新类型的实际网格、动态组件、材质及技能资产要按其构造路径解析。
   这是确定的准备范围遗漏；尚不能说它造成了之前全部十秒卡顿。

2. 渲染注册 fence 完成 ≠ GPU 运算完成 ≠ 每实例 SkinCache/光追结构已准备 ≠ 纹理有驻留余量。
   现有 PSO 模板没有注册到场景，本来就不负责预生成这些资源。下一批要扩展准备阶段，不能把已有“Ready”继续当成全部就绪。

3. 当前规则以迎宾精英死亡解锁主题出口；普通员工、囊袋投手和增援仍有独立波次与房间完成统计。
   提前准备实例若直接填入现有 Slot.Monster、运行 BeginPlay/AI、开启计时器，可能提前改变波次、门锁、击杀和随机位置结果。
   必须分开“已准备”和“已加入战斗”，按当前代码保留规则，不能依据旧文档恢复成清完整个大厅才开门。

四、冲突取舍

现有做法 / 拟议做法 / 取舍

分帧生成 / 另加一个刷怪调度器：重复排队、叠加等待，难以判断真正积压。保留一个 FacilityHallSpawnSubsystem，扩展任务阶段和队列指标。

显存超预算 / 整波甚至整图隐藏怪物池：CPU 创建峰值可能下降，但常驻资源上升，可能加重持续低帧。资源余量治理优先；只准备有预算承受的近期实例。

PSO 完成 / 直接认为 GPU 预热完成：准备覆盖不一致。独立记录类、材质、PSO、实例注册及实际渲染资源阶段，不用固定等待秒数冒充完成。

远房 SetVisibility(false) / 认为资源已卸载：隐藏主要减少可见渲染工作。GenerationResources 等引用仍可能保留资产；共享网格还被近房使用时也不能释放。逐资源归因后拆开渲染驻留与逻辑依赖。

多怪物 AI 降频 / Actor Tick 全局变慢：NurseZombie::Tick 内推进攻击接触、冷却、恢复状态，可能改变命中与受击。先错峰周期知识更新、去重稳定查询，不降低战斗时钟和角色移动精度。

动画共享 / 全怪物直接换 Leader Pose：现有原生动画代理、独立受击、衣物曲线和击倒恢复需要逐类适配；共享动画评估不代表每只怪物的 GPU 变形与绘制都消失。列为后续有条件项目。

Morph 热点 / 把衣服拆成更多组件：可能缩小参与修正的顶点范围，也可能增加 draw calls、组件和骨骼复制。必须比较整体成本；本批不先拆模型。

回收闲置预览 / 每波强制 GC：立即全量 GC 本身可能造成长帧。沿既有缓存回收与正常 GC 生命周期，不把强制 GC 放进刷怪热路径。

五、分批实施顺序

A. 先补准备遗漏、明确资源预算（收益：针对首用卡顿和持续低帧优先；玩法风险低）

文件入口：Dungeons/AuthoredDungeonGenerator.cpp、DungeonMonsterRenderPreparation.h、FacilityHallEncounter.cpp；现有 F6 资源采样与 Tools/Performance。

做法：
 - 从本局实际种子选择得到同一份怪物资源配方，覆盖随机精英与会在其首次战斗使用的依赖，避免把全游戏怪物一次载入。
 - 延用现有 PSO 队列和异步加载；保留已修好的材质用途标志。
 - 区分纹理、骨骼变形/蒙皮、光追结构、场景常驻和编辑器预览的占用。只有查出持有者和实际释放效果，才能给资源回收项确认收益。
 - 首先回收已不用的预览/临时渲染对象和过度保留的资源引用；房间资源更深层拆分排在明确依赖之后。
 - 已知峰值超预算约 632 MiB，可暂以战斗开始前约 1 GiB 余量作为初始规划参考，最终额度由本局 50 怪、尸体、技能峰值决定；不是保证满足所有场景的常量。
 - 同时记录排队长度、最长等待、准备阶段耗时和显存余量，扩展现有 F6，不新增另一套面板。

约束：Quick 模式不经过完整预加载的 45% 纹理池策略；不要盲目扩池、清 DDC，或照旧教程增加本机引擎已弃用的 SkinCache 固定池上限。

B. 在原队列中提前准备真实实例（收益：主要降低生成峰值；玩法风险中，需生命周期隔离）

文件入口：FacilityHallSpawnSubsystem、FacilityHallEncounter，以及实际需要适配的怪物类/组件。

生命周期：计划槽位 → 资源就绪 → 实例准备 → 必要渲染准备 → 待激活 → 参与战斗 → 死亡展示 → 按原寿命退场。

做法：
 - 初批利用现有加载遮罩期间准备；后续批次利用确有余量的时段准备。只搬动准备工作，激活仍遵守当前波次、触发、位置和间隔。
 - 使用最终要参与战斗的同一个实例，不创建额外预览世界、替身或另一套怪物副本。
 - 准备状态不启动 AI、移动、感知、伤害、技能冷却、掉落或击杀统计；不能只靠 Hidden 标志。BeginPlay、自动 AI Possess、计时器和组件自动激活都要经过明确的激活入口。
 - SpawnActorDeferred 并不会自动把 FinishSpawning/组件注册拆成多个便宜步骤；把可提前的昂贵初始化显式分段，保留单次操作不可抢占的事实。
 - 只创建隐藏 Actor 不保证真正用到 GPU 资源。必要的渲染准备需覆盖实际使用路径，限定在加载遮罩内，并管理后续驻留；不使用游戏线程同步等待 GPU。
 - 准备队列有实例数和资源预算；预算包括活动怪物、已准备实例、尸体、技能及场景，不能只限制池大小。
 - 已有波次到期而准备未命中时，走现有受控生成路径并记录原因，不人为拉长波次等待来掩盖问题。
 - 保留随机流分域。不能因准备的顺序不同而提前消耗当前放置随机数；最终位置合法性仍在原规则要求的时点判定。
 - 取消本局、换区或销毁 Generator 时，取消任务并解除引用与回调，不能遗留准备对象。

效果边界：首次加载可能变长；真正要观察的是从进入到可顺畅战斗的总时间及战斗长帧。准备不解决 50 个已激活怪物每帧仍然过重的问题。

C. 给多怪物周期任务错峰和去重（收益：提高 CPU 规模余量；玩法风险低至中）

文件入口：Monsters/MonsterBTNodes.cpp、MonsterAIController.cpp、MonsterAwareness.cpp、MonsterWander.cpp。

做法：
 - 当前 Knowledge 服务每 0.1 秒运行、无随机相位。保持原有约 10 Hz 的正常更新频率，把首次周期更新时间按稳定 ID 分散，避免多只同时进入同一个周期。
 - 50 只即约 500 次周期调用/秒，60 FPS 下平均约 8.3 次/帧；这是量级说明，不是已经测得的开销或硬性每帧上限。
 - 受击、首次发现玩家、失效目标、攻击状态切换保持及时响应。只合并重复且状态没有变化的查询；同帧状态变了就失效缓存。
 - 在已有每只 0.65 秒寻路节流上统筹新请求，保留紧急重规划、公平轮转和最长等待约束。路径跟随和 CharacterMovement 继续正常执行。
 - 漫游与追击请求使用同一预算视图；已有群体警觉预算继续使用，不再叠一层相同限流。
 - AI 的重要程度看战斗关系，不只看是否在屏幕内。背后的攻击者、施法者、追逐者不能因为看不见就停逻辑。
 - 调度仅分散可延后的工作，不限制同时攻击人数，不把近身第 11 只怪物强制休眠。

效果边界：错峰降低峰值，去重才减少总工作量。若 50 只近身怪物的必要工作已经超出预算，不能承诺通过排队保持所有原始时限；要进一步定位真正的重复计算或持续渲染成本。

D. 整个游戏共同守住战斗预算（沿用现有机制，按证据继续）

 - 场景：分开房间可见性、渲染资源驻留和玩法状态；保持门锁、碰撞、导航、存档、共享实例组、阴影/GI 依赖及相邻房间及时显示。不能为了卸载远房而破坏追击或从门口看见的场景。
 - 角色：当前高顶点网格与衣物变形是 GPU 优化候选；先解决驻留压力，再判断剩余 Morph/蒙皮热点。只共享确实等价的动画输入与评估，不让独立动作或衣服状态串到其他怪物。
 - 尸体：保留现有落稳后冻结、活体优先、原寿命与查询碰撞。不开新物理池、不进一步降低预算。重用实例要等现有死亡展示结束，不能为下一波突然清尸。
 - 特效：复用 FPSImpactFXSubsystem 与 FluidPresentationSubsystem；提前准备本局必需的首用资源，关注击杀与下一波同帧的叠加。伤害结算、危险提示和投射物碰撞不得被视觉预算丢弃。
 - UI/装备：保留已有预览闲置回收和 HUD 查询修订；缓存只保留有用途的对象，不让每次开面板增加一个永久世界或全尺寸捕获目标。
 - 联机兼容：服务端决定 AI、命中、槽位和波次；客户端渲染准备完成不能成为服务端怪物是否活动的条件。可见性/相关性要考虑所有玩家，不只 Player 0。

E. 后置项目：仅在剩余热点支持时实施

 - 按怪物类型做完整 Actor 回收复用。先做高频、状态简单的类型；死亡回调、血量、装备、受击、AI、动画、布娃娃、特效、网络身份和槽位引用均需明确重置，不采用泛型反射遍历重置。
 - Animation Sharing：先考虑可共享的非战斗基础状态，保留独立攻击/受击/倒地及衣物曲线。CPU 共享收益不等于 GPU 变形输出或绘制实例消失。
 - Animation Budget Allocator 会主动降低部分动画更新或停止更新；当前 AlwaysTickPoseAndRefreshBones 还承担战斗姿态用途，不直接全量替换。
 - 衣物局部形变范围或子网格改造，需要计算新增 draw calls、组件、内存与所省变形工作，保持现有外观和穿插修正。
 - 远处降 LOD、降低阴影/更新频率属于可能改变表现的选项，未列入这批保画质方案。Mass/VAT/自研 GPU 群体渲染也不是 40–50 只完整交互敌人的首批改造。

六、公开项目和引擎方案能借鉴的部分

Valve《Left 4 Dead 的 AI 系统》：活动区域随幸存者移动，远处群体部分只保留数量，区域进入活动范围再实体化；这说明成熟项目会控制完整模拟的工作集。
可借鉴：按实际活动范围准备与分配成本。不能直接套用其销毁/抽象规则到本项目已存在的追击、存档和房间规则，更不能据此把屏幕外敌人直接删除。
https://cdn.cloudflare.steamstatic.com/apps/valve/2009/ai_systems_of_l4d_mike_booth.pdf

Saber《Space Marine 2 的几何渲染与着色器基础设施》：公开的是实例化、剔除、批处理与数据布局等渲染架构。展示的大规模实例数量不等于同样数量的完整独立 AI。
可借鉴：共享不变数据、减少重复提交、只更新实际需要的数据。当前项目先用已有 UE 系统，不照搬另一引擎或重写整个渲染器。
https://enginearchitecture.org/downloads/REAC_2025_Saber.pdf

七、将来比较方案的口径（本次未执行）

沿用当前随机地牢、固定种子、相同镜头/分辨率/画质/机器，分别比较首用与再次进入、第一波与尸体叠加下一波、普通战斗与技能叠加；20/35/50 只要记录实际全局数量及物种组合。
观察生成前后完整 10–20 秒，不只看恢复后最后十秒平均 FPS：CPU 游戏线程、渲染/RHI、GPU 分开看，记录 p95/p99、超过 50/100 ms 的帧数、排队延迟和显存预算越界持续时间。
GPU 和 CPU 的流水线耗时不能简单相加当帧时间。若把 60 FPS 作为规划目标，帧周期约 16.67 ms，必须为场景、玩家、技能和系统波动留余量，而非把全部预算分给怪物。
