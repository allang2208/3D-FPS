## 1. 持续慢帧主要落在 World Tick 之后

按相同单调时钟，逐帧计算：前段 = World.Tick 开始 − 前一 OnEndFrame；后段 = 本次 OnEndFrame − World.Tick 结束。后段是时间区间，不是某个函数的独占 CPU 时间，也不能直接命名为 Slate 或渲染耗时。

| 帧集合 | 帧时中位数 | World Tick 中位数 | Tick 后区间中位数 |
| --- | ---: | ---: | ---: |
| <20 ms，116 帧 | 10.03 ms | 6.06 ms | 2.86 ms |
| >33.34 且 <100 ms，139 帧 | 42.73 ms | 6.05 ms | 35.37 ms |

例子：11551/11553/11555/11557 分别约 41.60/41.62/42.02/41.77 ms；对应 World Tick 都约 6 ms，Tick 后均约 35 ms。穿插的 11552/11554/11556/11558 约 9–10 ms，World Tick 同样约 6 ms，Tick 后仅约 3 ms。

这排除了“普通慢帧主要由当前 World Tick 内角色/怪物逻辑变慢”的解释。现阶段应继续拆分 World Tick 之后的视口提交、Slate 更新/绘制、编辑器任务、编译资源处理和同步边界；数据还不能在这些候选中确定唯一原因。不要仅凭 Game P50=41.79 ms 去削减游戏逻辑，或仅凭 GPU 约 16 ms 直接降低画质。

World Tick 范围依据本机 `Engine/Source/Runtime/Engine/Private/LevelTick.cpp:1522` 与 `:2061` 的两个委托；它覆盖当前 World 的 Tick 主体，未覆盖后续完整引擎循环。

## 2. 496 ms 初始尖峰有渲染重建线索，不能只归给图标

帧 11303 的 496.14 ms 可分为：Tick 前 45.89 ms、World Tick 12.72 ms、Tick 后 437.53 ms。该帧 `Icon.CaptureSubmit` 只有 0.124 ms，整个 Icon.Tick 只有 0.131 ms；Capture 提交耗时并不包括 GPU 或渲染线程执行。

日志在该帧（日志帧号尾数 303）、15:53:52.690 记录 Persistent SBT 重建，NumShaderSlotsPerGeometrySegment 从 1 变为 2、NumGeometrySegments 从 0 变为 512；靠近该帧约 15:53:52.695 的结束点。下一条线程读数出现 GameWait 371.60 ms。

帧 11304 为 151.07 ms，其中 Tick 后 138.83 ms；再下一条 GameWait 为 88.15 ms。结合早先发现的发布边界不同，这些是启动/渲染准备及等待的强线索，尚不足以把全部尖峰归给 SBT 重建或图标。

当前读数 Draw=655.75 ms、DrawWait=1132.13 ms 也不能加到 496.14 ms 上；它们不属于同一个已对齐的计时区间。

日志在 15:53:53.494–53.645 还记录多张纹理在后台构建，包括 DW715 法线与 4K 纹理。它证明本次并非资源全部就绪的稳定状态，不证明这些构建分别造成了多少帧时。
