在 722 对相邻样本中，帧时与同一行 `Game+GameWait` 的相关系数为 -0.3875；与下一行读数的相关系数为 0.9949。这是本次采集存在明显发布边界错位的证据，不是允许统一把所有计时平移一帧的规则。

本机 UE 源码解释了边界差异：

- 面板在 `OnEndFrame` 读取单调时间和引擎全局计时：`FPSPerformanceMetrics.cpp:140`。
- `GGameThreadTime` 在视口绘制开始附近更新，测量的是相邻视口绘制入口之间的时间，扣除引擎记录的等待：`Engine/Source/Runtime/Engine/Private/UnrealClient.cpp:1832`。
- `GRenderThreadTime` 在 `PresentWindow_RenderThread` 中更新；该发布点按窗口执行，并非本面板的引擎帧边界：`Engine/Source/Runtime/SlateRHIRenderer/Private/SlateRHIRenderer.cpp:1286`、`:1328`、`:1359`。
- `OnEndFrame` 发生在本轮引擎帧号递增之前：`Engine/Source/Runtime/Launch/Private/LaunchEngineLoop.cpp:6127`。

因此，93.6 ms 尖峰附近有约 62 ms 的游戏线程等待读数，这是后续查等待来源的重要线索；还不能确定它等待的是哪项工作，也不能用本行 Game=9.4 ms 排除 CPU/同步问题。

A 开始连续 70 个样本的 Draw 小于 0.01 ms，之后出现 51.44 ms，再进入约 17 ms 的常态。当前没有计时发布序号、所属窗口和发布时间，无法区分这些读数反映了哪段窗口提交工作。不能把这些近零读数解释为场景渲染几乎免费，也不应凭值相同就判为陈旧。

建议：保留原始读数和现有“非同帧归因”合同，在界面中把此限制直接放到线程数值附近；本项目可控的 CPU 阶段用同一单调时钟记录起止范围。只有拿到发布端的帧号/时间或 Trace 关联证据后，才生成对齐指标。不要靠固定平移或把 Game、Draw、GPU 相加来修正。

## 4. 持续帧间波动尚未定位到具体系统

去重后 243 帧超过 25 ms；这些帧之间的 242 个间隔中，226 个恰好相隔 3 个引擎帧。短帧与约 30 ms 帧交替出现，平均 55 FPS 不能代表帧时间平稳。

当前可以排除“这段窗口正在大量重建图标/装备”的解释：图标动作和事件均为 0，玩家武器/衣装重建为 0。装备信息采集约 4.6–4.7 次/秒，并不是每帧 SceneCapture；其实际代码是在收集网格、材质和配件状态，现有次数本身不能证明它昂贵。

Game 有约 30 ms 的周期性高值，Draw 中位数约 17.5 ms，GPU0 中位数约 13.4–13.7 ms。但这些是包含编辑器/其他窗口的独立发布计时；尚不足以认定唯一瓶颈、指定某个网格，或直接选择降低 GPU 画质。

已记录的面板开销较小：快照生成平均约 0.72–0.73 ms、峰值 1.08 ms；UI 刷新平均约 0.40–0.52 ms、峰值 3.77 ms。46.67 ms 慢帧内只有约 0.83 ms 的 `Panel.Snapshot` 事件相交，93.6 ms 峰值没有已记录阶段相交。不能把面板事件当作整帧耗时解释。

B 捕获了 A 的导出过程：主线程 `Panel.ExportSubmit` 为 0.0325 ms；后台提交至完成的总墙钟时间为 16.498 ms。提交帧 217429 为 8.63 ms，完成标记所在帧 217430 为 15.44 ms。该 16.498 ms 不是主线程阻塞时间。

同窗口的 EOS 网络错误位于帧 217557/217558 附近，帧时为 29.32/7.99 ms，没有对应 93.6 ms 峰值；不能因日志含报错就将其判作该峰值根因。窗口前的仓库资产等待也不能搬入这个窗口归因。

下一步观测应覆盖项目 CPU 工作、UI 更新、动画/物理和等待边界，并保留与帧区间相交的阶段耗时；组件排名仍然只能作为复杂度线索。无法由项目埋点拆出的引擎内部等待，再由用户后续提供的 Insights 记录定位。本次未启动新采集。

## 修复优先顺序

1. **面板可靠性**：长帧分级、无条件保留最慢帧详情；线程发布边界和未知范围就近展示；失败名称与原因随 JSON 保留。
2. **归因覆盖**：补足本次周期性长帧涉及的 CPU/等待阶段，以及有限的历史长帧上下文；当前约 62 ms 的等待仍标为来源未定。
3. **功能缺陷**：处理 ASH12/AKM 配件材质的骨骼排列编译失败及图标回退。
4. **帧率优化**：原图标异步加载/共享装配/异步回读方案仍适用于首次生成路径；持续帧率优化按新增阶段证据选择对象。

本次与 13:15 旧导出的相机、组件覆盖及图标冷热状态不同，不能将约 15 FPS 到约 55 FPS 的差别写成受控优化收益。新版原始帧和事件导出已在用户采集中出现；图标繁忙路径、清空/停止等其他功能并未在这两份数据中得到运行确认。
