3. 为什么连玩家装备也会受影响
玩家和怪物各自有组件/输出资源，但经过相同 Morph/SkinCache 执行路径、图形队列和设备
资源管理。这里的“公共”是执行和调度路径，不是所有网格写进同一个顶点输出缓冲。
同资产 SK_SVCH_Refined_R5 的 Morph 在慢窗口中位数约 1.8863 ms，基线约 0.0233 ms，
恢复窗口约 0.0234 ms。玩家原有网格也受影响，不能将全部退化限定在员工衣服算法内部。
这些单网格事件按事件时间窗统计，与上面的完整帧口径略有不同。
本次玩家背包多数派发仍很快；整个 trace 中玩家 Jason 系列 SkinCache 派发只有 6 个
达到 1 ms，最大为皮靴约 2.795 ms。不声称所有玩家装备始终一样慢。

571 个 >=1 ms 的 MorphUpdate、6 个 >=1 ms 的玩家 SkinCacheDispatch：
- 全部落在单个已提交的 GPUWork 记录内部；UE 队列等待重叠累计为 0。
- CPU 提交到事件开始的间隔，中位数分别约 140.52 / 116.98 ms。
这支持排除这些区间的 CPU 未提交工作/已记录的 UE 跨队列等待作为直接解释，但提交到
执行间隔不能全算到该 shader 身上，也不排除 WDDM 抢占、换页或驱动内部等待。
GPU 时间戳跨度包含其间阻塞，不等于着色器指令的纯执行时间。

4. 输出缓冲并未在观察点持续换新
17 个有衣服 Morph 的组件（12 研究员、5 接待员）：
- 共享 Morph 输入：2 个唯一 RHI 缓冲，逻辑总大小 72,529,216 字节，约 69.17 MiB。
- 当前 Morph 输出：17 个唯一 RHI 缓冲，逻辑总大小 53,953,008 字节，约 51.45 MiB。
- previous 观察指向与 current 相同的资源，不重复计入内存。
- 每组件 RHI 地址、原生资源 ID、原生 GPU VA 的观察集合均未变化。
- 输出为 DEFAULT heap 上的 placed resource，输入也为 DEFAULT；不是把输出误放进
  CPU UPLOAD heap 的这类错误。
采样频率 <=2 Hz。稳定身份不证明每个中间时刻都无移动，也不能证明物理页一直在本地
显存。GetHeapProperties 的 UNKNOWN memory pool 和 DEFAULT heap 类型不提供这个答案。

本地预算余量从刷怪前约 1.3 GiB 降到慢阶段约 338～406 MiB；+6.35 s 观察到余量上升约
372 MiB，随后 +7.4 s 左右 GPU 恢复。此相关性不足以证明某个输出被迁回显存，且恢复后
余量又下降到约 320 MiB 而 GPU 仍较快，不能将单一余量阈值当成确定判据。
系统段统计也不是逐资源物理驻留记录。没有把逻辑资源清单大小当作实际显存占用。

6. 已修复：无装备变化时仍强制重建衣着
Source/FPSGAME/Characters/FPSPlayerBodyComponent.cpp，BeginPlay 的 Profile->OnChanged 绑定。
旧链：通用档案通知 -> RefreshEquipment -> bOutfitDirty=true -> CaptureEquipment ->
ApplyOutfit -> DestroyComponent/重建全部衣着组件 -> 重建对应渲染/蒙皮资源。
OnChanged 也用于状态、训练、容器等变化，不代表换装。CaptureEquipment 原本已按武器
配置键、衣着槽位/定义比较变化，旧绑定却每次绕过这项比较。
新绑定是绑定当前组件生命周期的 weak lambda，只置 bEquipmentDirty=true；EndPlay 仍通过
原 DelegateHandle 解绑。没有增加定时器、强引用或新常驻缓冲。

保留的路径：
- 初始 bOutfitDirty=true，首次装备正常初始化。
- 武器配置键变化仍重建武器并重新应用衣着，袖子/手套随武器正确接入。
- 衣着槽位/定义变化仍调用 ApplyOutfit。
- 显式 RefreshEquipment 仍强制刷新，现有工具/弓/蓝图入口语义不变。
- RefreshAppearance 独立按头发/头部状态刷新，不依赖本次移除的强制脏位。
- 主机为远端 Pawn 读取 GetNetShadowProfile，权威装备、ReplicatedOutfit 和 OnRep_Outfit
  路径不变；未把主机档案替代远端档案，也没有新增客户端权威决定。

本次 F6 的 frame 21932 包含首刷时刻，记录 outfit_rebuilds=1、weapon_rebuilds=0、
visibility_fields_changed=2。整个遭遇窗口也只有这一次衣着重建。
未记录该次重建的调用栈，不能证明具体哪条 OnChanged 广播触发它，更不能把它当成持续
数秒高 GPU 时间的完整解释。修复的是已确定的无关通知导致强制重建的代码路径。
