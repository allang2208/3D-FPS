结论与边界
1. 已修正确定的资源持有问题：身体预加载器把未选择的武器备用版本也整批加载，
   并通过 StreamableHandle 保留到 GameInstance 结束。现默认只保留原来的身体、
   类默认资源、库存预加载；额外字面量候选表需要显式开启诊断开关。
2. 实际运行确认：原策略请求 400 项（主资源 191，额外候选 209）；新策略请求
   191 项且 191/191 完成。新策略没有删除资产或改变正常装备加载路径。
3. 两组非瞬态 RHI 分配清单的战后总差为 392.214 MiB。其中 442 个武器 Owner
   条目、合计 316.109 MiB，在新策略清单中为零。这是资源分配/持有修正的证据，
   不是“腾出了等量物理显存”的证明；Owner 条目也不是预加载请求项数量。
4. 新抓到另一处明确阻塞：RHI 线程创建 Bindless GPU 描述符堆，42 次累计
   6261.79 ms，最长 656.8874 ms。它会阻塞共享提交链，涉及怪物和玩家装备。
5. 不能把上述 CPU 分配停顿直接当成此前持续 400 倍 GPU Normalize 的答案。
   22:43 慢状态的 2.784 秒 trace 内没有新建 Bindless 描述符堆，相关切换调用
   最长仅 0.0655 ms。那份慢状态仍指向 GPU 内部资源访问/驻留/调度，而非这类
   CPU 创建停顿。尚缺输出父堆到物理段、缺页/迁移的逐资源关联证据。
6. 没有获得可宣称 FPS 提升或根治的干净性能 A/B；不能将不同启动状态、PIE、
   独立游戏、离屏窗口尺寸和系统重启后的结果混为优化前后。

  Engine/Source/Runtime/D3D12RHI/Private/D3D12BindlessDescriptors.cpp
    AddActiveGPUHeap：优先复用池；池为空时调用 CreateGpuHeap。

400 倍问题的继续定位
- 22:43 原始慢态：迎宾员相同 162110 顶点的 Normalize，有些派发中位约
  0.0082 ms，另一些约 3.17–3.75 ms。派发序号不等于可靠 Actor ID。
- MorphTargets.usf 的 Normalize 只访问形变输出，做六个分量的转换与写回；
  不读压缩 Morph 输入或骨骼。这把重点缩到了输出访问与 GPU 内部等待。
- 该次已观察到的 17 个独立输出合计 54.36 MiB；current/previous 别名不能
  重复相加。输出均为 placed DEFAULT 资源；稳定 GPU VA 不等于稳定物理驻留。
- 该慢态 220 个超过 1 ms 的 Normalize 都在已提交 GPUWork 内，记录到的
  UE 队列等待交集为零。仍不能排除未被 UE 时间线覆盖的驱动调度/访问等待。
- 同 PID/LUID 的 D3DKMT 原始辅助计数显示，慢态 local Demoted 约
  480–693 MiB，位于 normal priority 槽，nonlocal usage 约 829–1042 MiB。
  这些结构被 Microsoft 标为系统保留，不是受支持的逐资源物理驻留接口。
- 本轮重启后的 A2/B2 中，39 只怪全部正常存在，迎宾员 8 组 Normalize 的
  中位都约 0.0082 ms，研究员约 0.0062–0.0072 ms，霜剑手臂约 0.0031 ms；
  两组 raw Demoted 都为零，nonlocal 约 286/295 MiB。
- 甚至旧常驻策略 A2 也已正常，说明候选资源修正不是本次恢复的单一原因。
  这增强了资源/驱动状态相关性的证据，但尚未证明具体哪个父堆被放到系统内存。
- 重启后 A2/B2 的描述符堆创建分别 40/42 次，累计 39.44/41.85 ms，单次
  中位约 0.91 ms。与此前 42 次累计 6.26 秒相比，创建次数相近、耗时显著不同；
  运行环境和系统状态不同，不能把差异归功于候选开关。
