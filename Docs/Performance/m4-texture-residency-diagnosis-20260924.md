# M4 间歇性贴图模糊排查 · 2026-09-24

用户描述为已经进入游戏、M4 仍模糊或像缺贴图。排查期间用户确认画面随后恢复，不能稳定复现。本轮只读取工程、资产、当前运行状态和日志，没有修改游戏源码、材质、纹理或画质设置，没有主动打开、重启 UE 或启动 PIE。

## 目前结论

尚未捕获到恢复前的完整纹理流送状态，因此没有唯一确定根因。现有证据支持优先排查间歇性的 mip 请求／流送调度与资源竞争，而非重新迁移 M4 模型或重新下载贴图；这仍是排查方向，不是已证实的故障链。

- 当前实际持枪模型为 `/Game/Weapons/M4HK416Replica/SK_M4_FoldingSights_HK416`，运行时 `AKMViewmodel` 的八个材质引用均存在。
- 枪身颜色、法线和粗糙度原始资源均为 4096×4096；护木、原枪托为 2048×2048，原握把为 512×512，原消焰器为 256×256。资产 LODBias=0、MaxTextureSize=0，没有人为限制到小分辨率。
- 22:16:21 的当前 PIE 纹理列表显示枪身三张贴图均以 4096×4096 驻留，包含 13 个 mip。这个状态可能已经发生在恢复之后，不能用于证明此前从未缺失高清层级。
- 当次游戏采用 Quick 模式。实际纹理池约 3055.32 MB；统计中的剩余流送池为 2222.65 MB，目标资源约 291.62 MB（13%）。这份快照不支持“当时流送池已经超预算”的判断，也不能反推故障时的预算。
- 日志中的 `WeaponIcon: deferred ue_m4a1 ... reason=TextureStreaming` 是图标预览管线的等待，不能直接当作第一人称枪身低清的证明。

## 诊断命令对现场的影响

`ListTextures -CSV` 不是完全被动读取：本机引擎 `UnrealEngine.cpp` 中先调用 `UpdateResourceStreaming(0.f, true)`，后者会同步推进一轮流送调度。用户在排查期间报告恢复，因此无法排除诊断动作帮助推进了流送。这是诊断限制，不是修复，也不能以此宣称故障已解决。未执行关闭流送、永久强制驻留、增加纹理池或改变画质等命令。

后续若再次发生，应先使用只读取计数的快照保留 resident/requested/wanted mip、pending init/streaming、实际材质路径、池需求及时间戳，再考虑会推进流送的命令。未在本轮新增运行时监控或自动测试。

## 另外发现的具体问题

- 已加载的天空 HDR 中，六张 4096 立方纹理各占约 768 MiB，一张 2048 立方纹理约 192 MiB，合计约 4.69 GiB，都是非流送资源。总 Non-Streaming Mips 统计约 5396.40 MB；它们是需要优化的显存占用，但不能与剩余流送池直接相减或认定其必然造成此次 M4 模糊。
- 较早会话中四个地牢材质编译失败：`M_Earth_PebblePatch`、`M_Earth_Ridge`、`M_Earth_Pebbles`、`M_Earth_Gravel`。日志明确给出纹理采样器类型不匹配并回退默认材质。这可以解释对应地牢物件的缺贴图，和 M4 间歇性低清分开处理。
- M4 的贴图使用普通 World/WorldNormalMap 分组，当前持枪代码未维护专门的高清驻留请求；枪匠预览另有短时驻留策略。是否需要为当前手持武器建立有界保护，应依据故障快照决定。
- 原 M4 Roughness 资源仍开启 sRGB；这是材质数据解释问题，会影响表面观感，不能解释“等待一段时间突然高清”的时序，故本轮未扩大修改范围。

## 证据

- `asset.json`：磁盘资产引用、纹理规格和 mip 设置。`compiled_resource_textures` 在无渲染 commandlet 中可为空，不能解释为材质没有贴图；独立的 `dependency_textures` 为资产注册表依赖。
- `runtime.json`：当前 PIE 实际组件、材质、纹理和 cvar。
- `runtime-streaming-snapshot.log`：22:16:21 的原始统计与纹理列表。
- `earlier-runtime-evidence.log`：早先 Quick 模式、M4 图标等待、地牢材质失败的带原始行号摘录。
- `read_runtime.py`、`read_asset.py`：本轮诊断脚本；运行时脚本包含会推进流送的 ListTextures，不应当作零扰动采样工具。
