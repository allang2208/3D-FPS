# 篝火 UI、代码与内容审计（2026-10-26）

## 范围与结论

本轮按用户要求审计当前工程中的篝火：打开与关闭面板、食材选择、批量排队、添柴、烹饪结算、领取、拆除返还、食品腐败、建筑存档、主客机请求、取暖减耗，以及模型／图标／声音／烤架显示的接入。仅新增本记录，未修改生产代码、配置、资产或玩家存档。

执行了源码阅读、当前 JSON 配置读取、资产文件存在性检查和 PNG 尺寸读取。没有启动 UE 编辑器、游戏、commandlet、构建或多进程测试，没有截图、渲染或试听。以下区分可由代码确定的问题、性能改进点与内容缺口；不把历史测试结果算作本轮验证。

现有四条配方和公共交易主流程均已实现。优先处理顶部内容无限增高、燃料需求口径和状态反馈，再完成狩猎肉类的烹饪链。无需重做取暖或公共库存架构。

## 确定的问题

### P1-01：公共成品及队列撑高顶部卡片，挤占可操作区域

- 位置：`Source/FPSGAME/Building/CampfireCooking.cpp:14`、`:254`，`Source/FPSGAME/UI/ColdSteelCampfireWidget.cpp:51`、`:66`，`Source/FPSGAME/UI/ColdSteelSmeltingWidget.cpp:133`、`:152`、`:223`。
- 每份熟食新增一个独立 Product，保留各自食品身份和腐败时间，这个存储语义是必要的。但 UI 直接逐项拼接名称与数量，没有做显示层汇总；60 份同类熟食可能显示 60 次“名称 ×1”。
- 最多八条等待订单也追加到同一个自动换行 TextBlock。该卡片没有高度上限或滚动容器，只有下方食材列表可以滚动。内容累积会挤占列表的 Fill 高度；矮窗口还有内容溢出风险。未做实际窗口渲染，具体溢出边界待视觉检查。
- 修复：显示层按品类汇总成品数量，保留各份真实 Payload；将当前加工、等待队列、公共成品分区，队列与成品设置有界滚动，投料／领取／添柴保持可达。不能为了省行数合并服务器食品实例而重置腐败时间。
- 对应场景：连续加工同一菜品、不领取直到接近 60 份，并保留八条等待订单；在窄／矮窗口查看。

### P2-02：燃料“还需烧”只算当前一份，不能代表整批或全队

- 位置：`Source/FPSGAME/UI/ColdSteelCampfireWidget.cpp:73`，`Source/FPSGAME/UI/ColdSteelSmeltingWidget.cpp:1011`。
- `CdNeed` 只写入当前配方的 `Seconds - Progress`，燃料卡据此显示“还需烧”并判断不足。
- 例如刚开始加工五份大羊排时，总计约需 300 秒，面板却只提示当前一份的 60 秒；等待队列也完全未计入。
- 修复：分别显示“本份剩余”“当前批次剩余”“全部队列需燃料”，燃料不足提示使用总剩余需求。保留允许无燃料排队的既有规则。

### P2-03：鸡腿竖图在配方列表中被拉成方形

- 位置：`Source/FPSGAME/UI/ColdSteelSmeltingWidget.cpp:721`、`:1032`。
- 当前生／熟鸡腿 PNG 实际尺寸都是 320×640，但列表把图片装入 28×28 的 SizeBox，画刷尺寸也写死为 256×256，没有等比适配。
- 修复：外部图标格保持统一，内部按纹理真实长宽比等比显示，复用项目现有图标适配方式。无需重新制作鸡腿图片。

### P2-04：篝火操作失败和成功使用相同的中性提示色

- 位置：`Source/FPSGAME/UI/ColdSteelCampfireWidget.cpp:33`、`:94`，`Source/FPSGAME/UI/ColdSteelSmeltingWidget.cpp:1025`，`Source/FPSGAME/Multiplayer/ColdSteelCampfireRequests.cpp:95`。
- 篝火将全部结果作为字符串传给 `SetStatus`，没有传失败标志；默认显示次要灰色。保存异常、食材不足、不可达和成功领取难以快速区分。
- 修复：请求回执携带明确的结果状态；成功绿、失败红、等待／容量暂停黄、无操作灰。不要依靠中文字符串关键字推断成功与失败。

### P2-05：面板食材数量与服务端可烹饪数量口径不同

- 位置：`Source/FPSGAME/UI/ColdSteelCampfireWidget.cpp:81`，`Source/FPSGAME/UI/ColdSteelWarehouseModel.cpp:174`，`Source/FPSGAME/Building/CampfireSharedTransactions.cpp:18`、`:164`。
- 面板用 `CountMaterial` 累计定义相同的物品，服务端扣料会跳过已经腐败的实例。
- 通常腐败系统每秒把过期物品转换掉，但在转换前、客机旧镜像尚未更新或腐败转换保存失败时，会出现面板显示足够／按钮可点，而服务端拒绝“新鲜食材不足”。
- 修复：提供统一的“可用于烹饪的新鲜数量”查询，供列表、批量上限和提交前展示共用；服务器继续保留最终检查。队列和成品增加剩余保鲜提示。

## 代码与联机性能改进

### P2-06：同一座有工件且有燃料的篝火每次调度会结算两遍

- 位置：`Source/FPSGAME/Building/VoxelBuildWorld.cpp:737`、`:741`，`Source/FPSGAME/Building/CampfireCooking.cpp:194`。
- 第一轮遍历所有 SmeltingJobs，第二轮名为 IdleCells，实际加入所有有燃料的位置，没有排除已有工件的篝火。
- 0.1 秒调度一次，活跃篝火通常执行约 20 次／秒结算。当前 UTC 时间戳会随结算推进，因此不能据此声称“双倍烹饪／双倍耗柴”；确定的问题是重复复制工件、遍历食品及查询时钟。
- 修复：第二轮只处理没有已结算工件的燃料点，或先收集唯一位置再执行。没有采样帧时间，不能给出 FPS 收益数字。

### P2-07：篝火每次操作仍完整上传档案，增加客机等待

- 位置：`Source/FPSGAME/Multiplayer/ColdSteelCampfireRequests.cpp:35`，`Source/FPSGAME/Multiplayer/ColdSteelPlayerState.cpp:873`。
- 每次添一份木材、排队或领取都会序列化完整档案，冻结本地库存事务，按带宽分块发送后才提交篝火意图。已有通用库存入口在确认基线一致时可直接提交，参见 `ColdSteelInventoryRequests.cpp:59`。
- 修复：复用已确认库存基线，状态一致时直接发意图，需要同步时再走完整上传；保留版本校验、可靠顺序和回执。此项是确定的额外流程开销，未量测真实延迟。

## 内容与交互缺口

### C1：狩猎的三类肉尚未形成烹饪链

- `Content/ColdSteelData/wildlife.json` 已掉落 `raw_venison`、`raw_boar_meat`、`raw_fox_meat`。
- `items.json:6140` 起的定义明确标记没有对应菜谱、图标及世界模型；当前 `campfire-recipes.json` 仅有四条旧菜谱，也没有三类对应熟食定义。
- 这是已存在的未完成内容，不是本轮材料接入导致的回归。玩家取得这些肉后目前无法用篝火加工。
- 后续应一并制作生熟模型／图标、菜谱、营养效果、掉落展示、烤架展示和食用动作入口；不能只补三条 JSON 配方就宣称完整接入。

### C2：新增菜谱的三维展示与食用动作仍依赖硬编码名单

- `Building/CampfireCookingPresentation.cpp:17` 的四组数组及路径生成式写死四类食物；`Items/FPSPotionUseComponent.cpp:50`、`:147`、`:180` 也逐个匹配食物 ID。
- 当前四类可以匹配；将来只增加目录配方会缺少烤架展示或进食接入。
- 建议逐步集中到一张食品表现配置表，包含生熟模型、烤签锚点、动作类型和时序。继续保留现有羊排特殊穿杆点和双手食用配置。

### C3：F6 免材料没有覆盖篝火，属于现有功能范围之外

- `UI/DevelopmentTuningPanel.cpp:67` 明确列出打铁、制药、木工、枪械／弹药，没有篝火。
- `ExecuteCampfire` 始终扣食材及木材，篝火 UI 也必须持有食材才显示配方。
- 若后续要求扩展，需要同时处理免费投料、列表可见性、免费订单标识、拆除不返还未支付食材；燃料豁免应另行明确。不能只跳过扣料，否则拆除退款会凭空产生材料。

### C4：食品信息不足，配方不容易发现

- 配方列表只展示持有食材，未持有的配方完全隐藏；这是原实现的明确选择，本轮不视为新增故障。
- 当前行展示输入、输出、秒数和持有量，没有食物效果详情或悬停入口。玩家无法在面板比较鸡腿／羊排的饱食恢复、香肠的体力恢复效果、大羊排的体力上限效果。
- 建议展示完整菜谱、缺材料时禁用并说明原因，保留“仅看可制作”筛选；选择后显示效果、耗时、份数和燃料需求。列表、标题、按钮复用冷钢字体与横向排版规则。

## 本轮核对到的已有实现

- 四条有效菜谱：鸡腿 30 秒、羊肋排 30 秒、香肠 20 秒、大羊排 60 秒；每批 1–5 份，等待队列最多 8 项，公共成品容量 60 份。
- 八个生熟物品的 JSON 定义、世界模型文件和图标均存在。鸡腿两图为 320×640，其余六图为 320×320。这里只确认文件存在与图像尺寸，未反序列化 UE 包或验证材质画面。
- 篝火主体、烤架支架、烤签、当前火焰、蒸汽、滋滋声六项引用文件存在。四类食物与滋滋声有显式 cook 目录；ColdSteelData 由 Build.cs 整体作为 UFS 依赖包含。
- 材料来源：操作者背包、分区和主仓库；具名外部容器不参与。公共队列／成品共享，领取进入操作者背包；背包容量不足时允许领取可放下的部分。
- 服务器核对操作角色、存活状态、3.5 米距离、视线、真实篝火构件、批量和库存版本，并用请求序号防重复扣料。客户端读复制状态并外推显示倒计时。
- 写前日志先记录篝火目标状态，再提交操作者档案和建筑存档，失败保留日志并阻断继续交易；拆除在通用事务内时使用已有事务暂存路径。
- 食材托管保留原实例及食品时间，排队和成品都会腐败；领取返回原食品 Payload，不重新生成一份新鲜食物。旧档有食品托管迁移分支。
- 取暖仅服务器对有效燃烧篝火查询：5 米内饥饿、水分自然消耗各乘 0.5，多篝火不叠加。表现距离预算与减耗资格分离；不立即回血／补饥渴。
- 烤架展示和滋滋声读取公共快照，停火／结束／离开预算时停止烹饪效果。公共成品在燃料用完后仍可展示。

## 建议的实施顺序与后续检查范围

1. UI：顶部拆分、有界滚动、成品显示汇总、鸡腿等比图标、操作反馈颜色；保留统一字号和横排标签。
2. 数据口径：本份／本批／全队耗时及燃料、新鲜食材数量、食品效果与保鲜时间。
3. 代码：消除重复结算、复用联机确认基线，将食品表现映射集中管理。
4. 内容：补齐三种狩猎肉的完整加工与食用链；F6 是否覆盖食材和燃料按后续需求实施。

后续若进行运行检查，应覆盖满成品＋满队列的矮窗、五份大羊排的燃料提示、食品刚过期及保存失败、多人同时领取、请求期间死亡／重生、断线重连、存档失败恢复、拆除退料与食品时间保留。本轮没有实际运行这些场景，也没有证据据此宣布联机完全通过或发生死锁。
