# 随机地牢审计 — 2026-09-22

结论：现有三房池的随机布局算法在本次离线样本中能够生成连通、无非邻接占地重叠的布局，但房间扩展重建存在可复现的数据丢失缺陷；入口尺度、战斗导航、宝箱扩展及 Boss 汇流尚有缺口。不能把“拼接成功”当作整个战斗地牢已经正常。

本次只读审计，不修改生产源码、配置、地图或资产；没有启动 PIE、切换地图、编译、重启或联系其他任务。审计脚本、快照及结果仅写入本目录。编辑器读取经项目批次互斥桥执行。

## 依据及版本范围

- 初始源文件快照：2026-09-22 18:01（北京时间），散列见 `Results/snapshot.json`。
- 编辑器只读状态：`Results/editor-state.json`。当前地图 `/Game/GameMaps/L_Dungeon_Randomized`，未播放，预览种子 92247，70 个模块，2 个宝箱房。
- 活动目录只有 Distribution、Drainage、ShoredBreach 三种普通房，以及 Junction、RouteEnd、Transit、Threshold、Treasure、TreasureLink，共 9 种模块。
- 两款新房的独立目录已存在，但读取时没有 `DungeonRoutes20260922/Config/room-extensions.json`，活动生成器目录也没有 VentilationLoop / FreightTransfer。其导入回执仍为 `importing`，没有地图安装回执。应表述为“源模块已制作，活动池尚未接入”，不能把制作中状态当作已交付功能回归。
- Boss 合同明确写明 `room_pool_eligible=false`、`routing_status=contract_only_not_connected_to_runtime`。其制作中状态不是本次报告认定的已上线故障。
- 审计期间生成器装配部分发生并行更新，另保留 `Snapshot/AuthoredDungeonGenerator-final.cpp`（源文件修改时间 18:03:08）。两份快照中的 `FPort` 至 `FPlan` 结束完全一致，因此离线规划结论仍适用。没有尝试编译未确认完成的并行工作；不推断当前编辑器 DLL 已包含这些源码更新。

## 发现

### 1. P1：宝箱扩展和普通房扩展组合后，完整重建目录会遗漏新房模块

确定性离线复现，非猜测。

- `DungeonRoutes20260922/Scripts/build_catalog.py:54` 调用宝箱扩展。
- `DungeonTreasure20260922/Scripts/extend_catalog.py:13` 给 `catalog['modules']` 换成一个新列表。
- 后续 `build_catalog.py:61` 仍修改旧局部变量 `modules`，第 62 行却把新房名称加入 `catalog['room_ids']`。
- 结果：输出 `room_ids` 有五房，但序列化 `modules` 中没有 VentilationLoop 和 FreightTransfer。运行时 `AuthoredDungeonGenerator.cpp:290` 将二者查找为 -1，第 296–297 行拒绝生成。

复现使用真实构建脚本，只在内存中模拟新房注册文件，拦截所有 `Path.write_text`，没有写活动目录。结果见 `Results/catalog-probe.json`：`same_list=false`，`missing_room_modules` 正好是两款新房。

触发范围：完成两房注册后重跑完整目录构建。新房自己的 `install.py` 直接合并活动目录，本身没有这个旧列表问题；所以“直接接入曾成功”和“日后重建会失败”可以同时成立。

建议：后续扩展始终修改 `catalog['modules']`，或在宝箱扩展之后重新绑定局部引用；保存前核对所有 room_ids 都能唯一解析到模块。

### 2. P1（战斗接入）：当前随机地图缺少导航范围的建立和更新

- 编辑器只读枚举当前关卡，`NavMeshBoundsVolume` 数量为 0（见 `Results/editor-state.json`）。
- `DefaultEngine.ini:127–137` 虽然配置了多种代理及 Dynamic Recast，但生成器没有根据随机布局创建／更新导航范围、等待导航就绪的逻辑。
- `MonsterAIController.cpp:120` 的 `BuildNavigationBounds` 是编辑器帮助函数，并且位于 `WITH_EDITOR` 下，不能当作随机地牢的运行时导航接入。

影响：不能保证进入随机地牢后怪物能寻路追击；Dynamic 设置本身不提供导航覆盖范围。本次未刷怪实测，未把这项说成已复现的怪物行为故障。

建议：按完成后的布局预留导航覆盖，适配实际支持的怪物代理，并在敌人启用之前明确导航准备阶段。不要只给固定预览种子建立一块静态范围。

### 3. P1（大型敌人通行）：随机配管房仍使用 1.32 m 的旧入口

- 活动 `catalog.json:173–174`：Distribution.entry 的宽高为 132×238 cm。
- Transit / Threshold 则为 276×315 cm，其余多数门为 300×280 cm。
- `AuthoredDungeonGenerator.cpp:40,64–68,277` 只读取／对齐位置和法线，丢弃 width / height，没有门洞兼容性或代理净空判断。
- `PoisonMaggotMonster.cpp:42` 的胶囊半径为 70 cm，直径 140 cm；`DefaultEngine.ini:131` 对应导航代理半径也是 70 cm。按当前尺寸，1.32 m 门无法容纳该碰撞体。

固定起点的渐变连接件只解决固定起点接口；它不会改变随机池里每一个 Distribution 的旧窄门。这解释了房间扩大后仍可能出现明显瓶颈。

当前预览 69 条模块连接中，39 条两端声明宽高不同。宽高不同不等于每处都漏空：墙厚和端墙可能封住差异；本次没有把数据差异直接认定为可见破洞。可以确定的是，接口尺寸没有参与规划，而且存在小于现有敌人碰撞直径的通路。

建议：保留固定起始样板的原始入口语义，为随机战斗房提供标准门洞版本；将净宽、净高、墙厚／端面封闭及代理余量纳入端口合同和连接件选型。

### 4. P2（新增房接入）：两款新房不会生成宝箱支房

- VentilationLoop / FreightTransfer 的 `Config/modules.json` 均没有 side_sockets。
- `AddTreasureRooms`（生成器第 165–179 行）先做 10% 抽签，再遍历侧门；没有侧门时直接跳过，不会给其他房补抽。
- 在候选五房池离线样本中，新房出现 1566 次，占全部 3171 间普通房的 49.4%。这部分房间即使抽中也没有生成宝箱房的可能。
- 原三房池：301/3191 次抽中（9.43%），实际放置 272 间（8.52%）。候选五房池：312/3171 次抽中（9.84%），实际放置 140 间（4.42%）。差异同时包含侧门缺失和空间冲突跳过；不是“随机数 10% 写错了”。

建议：给新房补合法侧门和对应墙体变体；或明确设为不参与宝箱的房型，并把 10% 的分母定义为符合条件的房间。继续保留先规划主路线、支房占地通过后才打开父房墙面的做法。

### 5. Boss 汇流属于未接入功能，现有算法不能自动承接

- 当前 `FPlan::Build` 第 139–151 行建立三条向外分散的支路，每条最终放一个 RouteEnd。
- `Place` 第 86–94 行将支路房间限制在向外的扇区。它没有目标入口搜索，也没有三路汇到同一房间的步骤。
- Boss 的 `terminal-assembly.json` 要求先预留唯一 Boss 大厅和汇流室，再让上游三路接入指定门口；这是新的终端连通合同，现有规划器不消费它。
- Boss 大厅只有一个门；普通 Chain 第 114 行假定每个普通房有两个门，直接加入普通池会访问无效的端口 1。现有 Boss 合同禁止入普通池是正确做法。

建议：先保留 Boss＋汇流室占地及三个目标插口，再做支路通往目标插口的路径求解和必要转向；只有完整可达且无冲突才提交布局。不能只把末端 RouteEnd 替换成 Boss，也不能将 Boss 加入等概率普通房池。

### 6. P2（失败路径，源码评审）：装配失败时缺少完整的保留旧场景边界

以 `Snapshot/AuthoredDungeonGenerator-final.cpp` 为准：第 336 行先 ClearGenerated；资产解析和对象创建直到第 380、403 等处才执行。第 562 行已先填写 LayoutDescription，后续资源失败则在第 640–645 行停下。

普通规划失败会保留原几何；资源／组件创建失败则可能已经删除原布局并留下半成品。安装脚本以非空 LayoutDescription 判断完成（例如新房 `install.py`），这种判断不能区分“已规划”与“已装配完成”。当前活动目录 98 个显式资源引用均存在并有硬引用，所以本次没有观察到缺资源实发故障，也没有故意破坏编辑器资源来触发它。

建议：在清除旧布局前解析完必需资源，并提供明确的装配成功结果；安装器只在装配成功时保存。后续若保留分帧装配，等待 completed 状态而非说明文字。

## 已完成的检查与结果

1. 当前编辑器只读取得目录、布局图、硬引用和导航范围数量。
2. 离线模型使用 UE 5.8 `RandomStream.h` 的随机数更新和 float32 RandHelper 行为。种子 92247 的模块种类、朝向、坐标、连接及侧房数量与引擎保存图对齐：70 节点、69 边、2 宝箱房。
3. 现有三房池 0–199 共 200 个种子：200 成功；没有断图、非相邻 cells 重叠、遗漏端口或一个端口连多个模块。
4. 只在内存中加入两款新房后的五房池，同样 200 个种子：200 成功；上述图／占地检查同样没有报错。该样本不代表新资产已导入或新房碰撞已经实机测试。
5. 扩展目录合并缺陷以真实 Python 构建脚本确定性复现；所有写入截获在内存中。
6. 活动目录 98 个显式资源引用：未发现缺少 Content 文件或 ModuleAssets 硬引用。没有检查所有间接材质依赖或打包产物。

占地测试依赖目录中的 cells，故不能证明模型真实三角面／碰撞壳完全一致；相邻门口允许墙厚接缝重叠，也不将其报为穿模。没有运行 PIE、角色实际走位、怪物寻路、动态导航、渲染和打包测试。源码并行更新不等同于活动 DLL 已更新。

## 概率与分类的现状

- 普通房池已支持 room_ids；若没有该字段则回退到原三房。不是所有 modules 都参与普通房抽取。
- 抽取顺序随机，但放置可行性和回溯会改变最后分布；当前三房样本 ShoredBreach 约 6.46%，不是每种约 1/3。该结果是几何约束偏置，不单独定性为代码错误。若需要频率目标，需要显式权重／配额与可行性统计。
- 连接件、岔路、末端、宝箱支房已在代码中分角色使用，但很多角色仍依赖硬编码 ID。
- 物件目前随房间模板固定引用 parts / props / anchors；没有独立可配置的随机物件权重池。后续怪物、奖励和 Boss 终端还不能仅靠改普通房池完成。

建议处理顺序：目录合并缺陷 → 随机战斗房净空与动态导航 → 新房宝箱接口 → Boss 目标汇流求解；失败保存边界与新装配流程一起完善。
